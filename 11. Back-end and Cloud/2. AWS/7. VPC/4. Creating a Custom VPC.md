Now even if a CIDR address of `10.0.0.0/24` is used it shows available addresses as only 251 (and not 256 which is what cidr.xyz too would confirm). That is because AWS reserves some of the IP address for itself. ([link](https://docs.aws.amazon.com/vpc/latest/userguide/VPC_Subnets.html#VPC_Sizing)).

When a subnet is created, it by default has its 'Auto-assign public IP address' turned off. Now typically one of the subnets would need to be marked as public. That is done using the option 'Actions > Modify auto-assign IP settings'. And the once this is done, it will be possible for instances launched in this subnet to get public IP addresses.

###### 4. Route Table

A `Route Table` contains a set of rules, called routes, that are used to determine where the network traffic from subnet or gateway is directed. ([Reference](https://docs.aws.amazon.com/vpc/latest/userguide/VPC_Route_Tables.html))

There is a main route table that already comes with a VPC, and controls routing for all subnets that are not explicitly associated with any other route table. A subnet can only be associated with one route table at a time, but multiple subnets can be associated with the same subnet route table.

It seems that the main route table is configured as public by default. The recommended practice is to make it private, and have a separate route table for all the public connectivity.

###### 6. Create security group for private instance

The private subnet's EC2 instance has a private IP. However this obviously cannot be ssh-ed yet from a ssh connection to the public subnet's EC2 instance. To do that, the security group of the private instance needs to be modified.

<span style="font-weight:normal"> 1. Create security group and allow traffic from public security group (or public subnet?) </span> | <span style="font-weight:normal"> 2. Private EC2 instance Actions </span> | <span style="font-weight:normal"> 3. Change security group for private instance </span>
--- | --- | ---
![](assets/Misc-287f476e.png) | ![](assets/Misc-3fb1b9ad.png) | ![](assets/Misc-c4a29235.png)

And now it becomes possible to SSH into the private instance, from a SSH connection to the public instance.

<span style="font-weight:normal"> 1. Copy pem on to public instance via `nano`</span> | <span style="font-weight:normal"> 2. `ls-l` shows the pem </span> | <span style="font-weight:normal"> 3. Now connection can be done and verified via `ping` </span>

![](assets/Misc-e5a4d816.png) | ![](assets/Misc-5db43dfc.png) | ![](assets/Misc-2c99fc62.png)

> Putting a pem file in an instance via a `nano` command is not a good way to connect from one instance to another. Bastion Hosts must be used instead.
