#### Snapshots

`Snapshots` are point-in-time copies of EBS volumes. They are stored in S3 and are incremental backups, which means that only the blocks on the device that have changed after the previous snapshot are saved. Each snapshot contains all of the information that is needed to restore the data (from the moment when the snapshot was taken) to a new EBS volume. ([reference](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/EBSSnapshots.html))

Snapshots can be found in Snapshots section.

![](assets/Misc-73bc6311.png)

###### Creating Snapshot

A snapshot can be created off a volume as well as EC2 instance.
> In case of EC2 instance, it probably creates a snapshot if its root volume?

![](assets/Misc-a1d52afb.png)

To create a snapshot for root volumes, the instance should be stopped before taking the snapshot. This basically ensures that snapshots are consistent.

This image can then be deployed to another AZ. In this new AZ when a new EC2 instance is created, it can use this new image (AMI).

###### Virtualization Type

While creating an image, `Virtualization Type` needs to be selected as well.

There are 2 virtualization types offered by AWS - `Hardware-assisted virtualization (HVM)`, `Paravirtual`.

With HVM virtualization, the guest VM runs as if it were on a native hardware platform, except that it still uses PV network and storage drivers for improved performance. Some instance types support both PV and HVM while others support only one or the other.
> What does all this actually mean?

Some instances support both virtualization types, while some support only one. HVM is the one that is supported by most instances.

#### AMI types

While launching an instance, AMI can be selected based on many different factors - region, OS, architecture (32-bit or 64-bit), launch permissions, as well as storage type for root device. It can be of two types.

1. `Instance store (ephemeral storage)` - Root device is a volume created from a template stored in S3.

2. `EBS backed volume` - Root device is an EBS volume created from EBS snapshot.

An `Instance store` provides temporary block-level storage for your instance. This storage is located on disks that are physically attached to the host computer. Instance store is ideal for temporary storage of information that changes frequently, such as buffers, caches, scratch data, and other temporary content, or for data that is replicated across a fleet of instances, such as a load-balanced pool of web servers. ([reference](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/InstanceStorage.html))

###### Only some instance types are compatible with Instance Store AMI

Usually the AMI type selected is EBS backed volume, but Instance store AMI can also be selected. However, only some instance types are compatible with an Instance store AMI.

###### More Instance store volumes can't be later added for Instance Store AMI

In Add Storage section, volume type then shows up as Instance Store. However, with instance store AMI additional instance store volumes cannot be attached to it later on. They have to be added right then (where is the option). Additional EBS backed volumes can be added later on as well.

![](assets/Misc-541c82a5.png)

> Instance stored volume cannot even be seen in `Volumes` section.

###### Instance Store AMI and possible data loss

If an instance store volumes is stopped or if its underlying host fails, the data is lost.
EBS backed instance can be stopped without any loss of data.

Both AMI types can be rebooted though, without data loss.

If instance is deleted/terminated, root volume is deleted if its an instance store volume. This behavior can't be disabled.
