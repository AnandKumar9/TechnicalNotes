Things such as CPU, wi-fi, bluetooth and baseband radios (EDGE, 3G, etc.), Core Location, accelerometers, disk must be optimized as well as possible in the code to minimize the battery consumption.

An app should do polling only when needed (what is polling?). Polling prevents the CPU from going to sleep. Instead of polling, use the NSRunLoop or NSTimer classes can be used to schedule work as needed.

The idleTimerDisabled property of the shared UIApplication object should be left to the default NO whenever possible. This allows the system to turn off the screen in case of inactivity.

While dealing with disk, it is better to do a single larger operation that accesses the disk instead of multiple short operations.

Drawing is an expensive operation and should not be done any more intensively than needed.

Delivery of UIAccelerometer events should be disabled (or the frequency reduced appropriately) when not needed.

While connecting to the network, the data should be transmitted in bursts instead of spreading the transmission over time. The system turns off the Wi-Fi and cell radios when it detects a lack of activity. When it transmits data over a longer period of time, the app uses much more power than when it transmits the same amount of data in a shorter amount of time. Hence, when using NSURLSession the operations should be coalesced together instead of starting one only once another has ended. NSURLSession internally takes care of performing them efficiently.

Wi-fi should be used instead of cellular data wherever possible, as it uses lesser power.

When using CoreLocation, location updates should be disabled as soon as possible and the distance filter and accuracy levels should also be set appropriately. Core Location uses the available GPS, cell, and Wi-Fi networks to determine the user’s location. Although Core Location works hard to minimize the use of these radios, setting the accuracy and filter values gives Core Location the option to turn off hardware altogether in situations where it is not needed.

Low memory conditions must be observed and responded to immediately in apps. Any unsaved important data must be saved and wherever possible unneeded references should be removed. The system delivers memory warnings to app using below APIs.
1. UIAppDelegate -> -applicationDidReceiveMemoryWarning:
2. UIViewController -> didReceiveMemoryWarning
3. UIApplicationDidReceiveMemoryWarningNotification
4. Dispatch sources of type DISPATCH_SOURCE_TYPE_MEMORYPRESSURE (This is the only one that can be used to distinguish the severity of the memory pressure).

UIRequiresPersistentWiFi is an info.plist key that can be used when an app requires persistent wi-fi connection even if the app is in background. This works only with wi-fi (and not cellular connection) and is particularly useful for internet radio apps. By default, the system automatically turns off the wi-fi hardware in case no app with this key has requested it for 30 mins. Hence this key allows the wi-fi hardware to be used for app’s life cycle. However if the device becomes idle (that is screen locked), this key is ineffective and even if the app may run the wi-fi hardware will not be used.
Further, the inclusion of this key also makes the system display a network selection dialog if it detects any wi-fi hotspot. Also if the app is launched with airplane mode enabled, a system alert is displayed if this key is set to TRUE.
