#### Sequence protocol

A `Sequence` can be thought of as anything that is series of values of same types that can be iterated. The simplest way to iterate over it is using a for in. <br>
`for element in someSequence { .. }`

This protocol also provides default implementations for some of the methods (such as `filter`, `map`, etc.)

The only required method in the `Sequence` protocol is `makeIterator`. This method should return item of the type `Iterator`.

An `Iterator` type is something which conforms to `IteratorProtocol` protocol. With the default implementation of `Sequence` protocol, the conforming type itself is returned as the iterator by `makeIterator` method. Iterator below is an associated type in the Sequence protocol. <br>
`func makeIterator() -> Iterator`

> Be creative and imaginative when thinking what types can be made sequences. Anything which has a sequential nature to it can be. For example structs whose instances store a couple of related numbers that logically change over successive instances or even otherwise if a single instance by itself needs to be iterated in some way (check the PrefixSequence example in page 53 of the Advanced Swift book).

So if you want a custom type to conform to `Sequence` protocol, don't hesitate in creating another type (very often a value type such as struct) which will be its iterator and would maintain the state in some way.

`last(where:)` - Returns the last matching element. <br>

 #### IteratorType protocol

It just has one required method called `next` which should give the next element in iteration. So two obvious things are clear from this. One that the `Iterator` should maintain a state. And two, that the type returned by the next method should be the same type that actually conforms to the `Sequence` protocol.

`mutating func next() -> Element?`

The fact that the `next` function is declared as `mutating` even implies that the iterator can also be a value type such as struct. This is needed as it the iterator needs to keep track of the state and it has to be kept through some property. Element above is an associated type in `IteratorType` protocol.

So if you think, `Sequence` protocol has an associated type called `Iterator`. This type conforms to the `IteratorType` protocol and that protocol has an associated type called `Element`, which indicates the type that adopted to the `Sequence` protocol to begin with. So the type can also be referenced using `Iterator.Element`.

In fact, Swift 4 onwards `Sequence` itself has an `Element` associated type, so now `Iterator.Element` can be simply replaced by `Element`.

As the `IteratorType` protocol only has a `next()` method but not a previous method, by definition iterators can only be advanced and not reversed or reset. Usually when the `next()` returns `nil`, that indicates the end of sequence. So if an iterator never returns nil, it will be a never-ending sequence.

Usually itretors have value sematics, in the sense that when assigned variable to another an actual copy is made.

#### AnyIterator, AnySequence, stride functions

There are two functions `stride(from:to:by:)`,  `stride(from:through:by:`), that actually returns a sequence type which iterates to or through the start to end values.
```
for x in stride(from: 5, to: 10, by: 0.5) {
    print(x)
}
```

Now the iterator of the sequences returned by `stride(from:to:by:)` and `stride(from:through:by:)` is of type `StrideToIterator`. And it too indeed is a value type (as most iterators are).

`AnyIterator` is an iterator that wraps another iterator as a reference type. So when passed around they all actually point to the same iterator. It is actually used when the actual type of the iterator needs to be hidden as it may in turn give away the type of sequence. `AnyIterator` also has an initializer that directly takes the next function as its argument.
And then to go with it, there is also a corresponding sequence type called `AnySequence`. It has an initializer that just takes an iterator as its argument.

> Just something to keep in mind. The sequence functions do not invoke their next closure unless asked for. This goes along with the lazy paradigm.

#### Unstable sequences

Now the thing to note is that, `Sequence` protocol does not require its conforming type to return the same values when iterated again and again. So while things such as arrays and dictionaries do not actually modify their values during traversal, this is not a mandatory requirements for types conforming to Sequence protocol. If it did modify it through during traversal, that is what is called as a `destructively consumed sequence or an unstable sequence`.

One of the methods in `Sequence` protocol is `enumerated`. It returns a pair of incrementing offset and sequence value that can be iterated through. The weird thing is that offset ie even returned for things such as dictionaries and sets. In fact even the order seems to be the same every time it is called.

```
let arr = [3,2,4]
for item in arr.enumerated() {
    print("\(item.offset) - \(item.element)")
} // Prints 0 - 3, 1 - 2, 3 - 4

let dict = ["city1": "Phildelphia", "city2": "Washington D.C.", "city3": "Baltimore"]
for item in dict.enumerated() {
    print("\(item.offset) - \(item.element.key) - \(item.element.value)")
} // Prints 0 - city1 - Philadelphia, 1 - city2 - Washington D.C. and so on
```

In fact the return type of enumerated method is something called `EnumeratedSequence<T>` and it is nothing but that tuple like pair of offset and element.

#### SubSequence

Now `Iterator` is of course an associated type in `Sequence` protocol. There is another associated type called `SubSequence`. This is the type that is returned when accessing a slice of the original sequence. So methods such as `prefix`, `suffix`, `split`, etc. actually return the `SubSequence` type. Unless explicitly specified as something else, it is automatically inferred to be of type `SubSequence<Iterator.Element>`. If there has to be separate `SubSequence` type then the protocol's required methods such as prefix, etc. need to be implemented.

#### Collection

Now conceptually `Collection` is any `Sequence` that is strictly non-destructive when iterated multiple times and is accessible using subscript syntax.

Technically, `Collection` is a protocol that inherits `Sequence` protocol and then of course adds its own things on top of it. So it has all the `Sequence` methods and then some more.

The common collection types in the standard library are `Array`, `Dictionary`, `Set`, some 4 String views (?), `CountableRange`, `UnsafeBufferPointer`. In fact there are other types such as `Data`, `IndexSet` too that conform to `Collection` protocol.

The only required methods in `Collection` protocol are `startIndex`, `endIndex`, subscript implementation and `index(after:)`. Keep in mind that `endIndex` actually denotes the index after the last index, so it is not a valid index itself.

Now the thing is that in addition to the two associated types that Sequence has (Iterator and SubSequence), Collection itself requires two more associated types. IndexDistance and Indices. IndexDistance probably already has a default type of int and Indices of probably IndexSet (but I think there is more to the syntax of Indices).

While Array Index is of type Int, for other collections it can be of other type too. The type just has to conform to `Comparable` protocol. Even Dictionary actually has an internal index type that is indeed something like Int, its just that when a key is used in the subscript notation it is actually using that internal index type.

When an element is removed from a dictionary, it apparently invalidates all its internal indices.

##### MutableCollection

A collection that supports subscript assignment (i.e. the collection is mutable).

`swapAt(_:_:)` - (This was introduced in Swift 4.0.)
```
var numbers = [1,2,3,4,5]
numbers.swapAt(0,1)
```


##### RangeReplaceableCollection

`RangeReplaceableCollection` is a protocol that supports replacement of an arbitrary subrange of elements with the elements of another collection.

`removeAll(where:)` - Mutates a collection by removing all elements that are matched by the passed closure.

#### ExpressibleByArrayLiteral -

If a type conforms to `ExpressibleByArrayLiteral` protocol, it can be expressed using array literal syntax. For example if any array is assigned [1,5,2] you know its an array with those items and in that order. Similarly Dictionary and Set also have their own implementation of this protocol and can be expressed using array literal.

Keep in mind though that by default an array literal represents an Array. So [1, 4] without having any other context attached to it would indicate an Array (and not a Set or anything else).

The only required method in the `ExpressibleByArrayLiteral` protocol (i.e. the method that needs to be implemented by a type to make it expressible using array literal syntax) is `init(arrayLiteral: Element...)`.
