#### Phases in a program lifecycle

Typically any developed code goes through these phases. (Now to be too theoretical there are other phases such as distribution and installation too, but not looking at those here.)

Compile <br>
Link <br>
Load <br>
Run <br>

`Compile time` - Source code gets converted to machine code. The result is an object file  (probably usually an executable). As a part of compilation, the source code's syntax compliance is also checked.

`Link time` - Links together all the machine code components of the program. So the way I understand it currently is that a program may have multiple components (i.e. libraries). While compile time converts all of them to machine code, link time is what links them all together.

There are two types of linking. When linking is done by compiler, it is called static linking. It always happens prior to execution (i.e. run). When linking is done by OS, it is called dynamic linking. It happens just before (or at times, even during) program execution.

`Load time` - OS takes the program's executable from storage (such as hard drive) and places it in active memory to begin execution (such as RAM).

`Run time` - Execution phase, CPU executes the program's final machine code instructions.

##### Compile time

A compiler typically performs several operations - Preprocessing, lexical analysis, parsing, code optimization, code generation.

`Cross-platform compiler` - If the compiled program can run on a CPU or OS different from the one on which the compiler itself ran, the compiler is called a cross-platform compiler.

`Bootstrap compiler` - A compiler written in the language that it intends to compile.

##### Link time

To put it very simply a linker takes one or more object files generated by the compiler and combines them into a single executable file, library file or another 'object' file.

Operations performed at link time typically include fixing up the addresses of externally referenced entities and cross module checks (i.e. type checks in external modules, etc.).

Even the thing generated by a compiler is termed as an 'object' file. Now the thing is that an object file at this stage consists of symbols that the linker then works with. The linker resolves these symbols and eventually generates a unified executable program.

Linkers can also take objects from a collection termed as library.

In case of `dynamic linking`, the resolution of some of the undefined symbols is deferred until a program is run. So the executable code contains undefined symbols and also a list of objects or libraries that will provide definitions for them. The final linking actually gets done in load time in such case. Hence, its even written that dynamic linking actually does not require any linker. As expected, there are both pros and cons to this approach.

In case of `static linking`, the linker actually resolves all the symbols during link time. This may of course require more disk space than dynamic allocation but it is also results in safer executable and no missing thing gets left to be caught only later on.

##### Load time

During load time the program is placed into memory and then certain preparatory tasks performed. And then the control is passed onto the loaded program code.

Embedded systems typically do not have loaders and instead the code executes directly from ROM.

In any case, loading and resolving any dynamic links otherwise is one of the primary tasks in the load time.

#### Interpreted languages

Not all languages are compiled, i.e. not all languages are first converted need to be converted to a machine code before it can be run. There are certain languages know as `Interpreted languages` that can be directly executed by something known as `Interpreter`.

Python, Perl, Ruby are all examples of interpreted languages.
