###### MTLDevice  -

`MTLDevice` is a protocol that represents the GPU. So any object properly conforming to it actually represents a GPU. Any custom class should not be made to conform to it, the system provides an object that conform it. Most of its methods create non-transient objects, including command queues, resources (buffers and textures) and pipeline states. These objects are expensive to create and should be created as early as possible and then reused throughout.

Its underlying type changes based on device as well as depending upon you are running on debugger or not (for example on debugger the type is `MTLDebugDevice`, but in real non-debug runtime it might be something else). This is probably a recurring theme across most protocols in Metal, the exact concrete underlying type is abstracted and does not really matter.

###### MTLRenderPipelineState -

`MTLRenderPipelineState` is a protocol that specifies the graphics functions, state, etc. used in the render pass. Again, a custom class conforming to it should not be created. A conforming object is given by the `MTLDevice` by passing a render pipeline descriptor to it.


******************

###### MTLRenderPipelineDescriptor  -

`MTLRenderPipelineDescriptor` is a class that configures new pipeline state objects. The shader functions are actually specified in a pipeline descriptor.

```
let pipelineStateDescriptor = MTLRenderPipelineDescriptor()
pipelineStateDescriptor.vertexFunction = vertexMetalFunction
pipelineStateDescriptor.fragmentFunction = fragmentMetalFunction
pipelineStateDescriptor.colorAttachments[0].pixelFormat = .bgra8Unorm

try? pipelineState = metalDevice.makeRenderPipelineState(descriptor: pipelineStateDescriptor)
```

******************

###### MTLRenderPassDescriptor  -

A render pass descriptor encapsulates the basic behavior for a frame buffer, i.e. what layer texture is is tied to, what should be its loadAction, what should be its clearColor, etc. A render pass descriptor in turn gets tied to the render command encoder.

```
let renderPassDescriptor = MTLRenderPassDescriptor()

guard let drawable = metalLayer.nextDrawable() else { return }

renderPassDescriptor.colorAttachments[0].texture = drawable.texture
renderPassDescriptor.colorAttachments[0].loadAction = .clear
renderPassDescriptor.colorAttachments[0].clearColor = MTLClearColor(red: 221.0/255.0, green: 160.0/255.0, blue: 221.0/255.0, alpha: 1.0)

guard let renderEncoder = commandBuffer.makeRenderCommandEncoder(descriptor: renderPassDescriptor)
else { return }
```

It has attachments - `colorAttachments`, `depthAttachment`, `stencilAttachment`. And of course many more things.

`colorAttachments[0]` is the buffer that would end up getting rendered to the screen eventually, so you nearly always work on it and not some other index of `colorAttachments`.

(A frame buffer is probably the frame data in memory that `CALayer` is handing over, don't confuse it with `MTLBuffer` which is used to store vertex data, etc.)


******************

###### MTLTexture -

It specifies a memory allocation for storing formatted image data that is accessible to GPU.
One common thing is to set the MTLRenderPassDescriptor's `colorAttachments` texture as the `CAMetalDrawable`'s texture.

```
renderPassDescriptor.colorAttachments[0].texture = drawable.texture
```

******************

###### CAMetalLayer, CAMetalDrawable -

In order to get anything on screen using Metal, the GPU (i.e. `MTLDevice`) has to be tied to the screen using a `CAMetalLayer`.
It should be attached to the view in some way (add layer or set it as the view's layerClass). Its also important that its device property is hooked to a `MTLDevice` object.

```
metalLayer.device = metalDevice
```

A `CAMetalLayer` gives a drawable object and the drawable object gives a texture object. And a texture is something that can be drawn onto (which API specifies that?). It represents the frame buffer. This texture should then be used in the rendering pass descriptor. And after setting up other objects, the rendering is finally done by using command buffer's present() method to present the `CAMetalDrawable` object.

```
let drawable = metalLayer.nextDrawable() else { return }

renderPassDescriptor.colorAttachments[0].texture = drawable.texture

.. after setting up the render encoder ..

commandBuffer.present(drawable)
commandBuffer.commit()        
```

`CAMetalDrawable` protocol basically represents a drawable resource that can be rendered by Metal. Its only properties are texture and layer.


There is a pixelFormat that need to be specified for the `MTLRenderPipelineDescriptor` (`colorAttachments[0].pixelFormat`). This needs to be same as that of the `CAMetalDrawable`'s texture's `pixelFormat`. Usually it is configured on the `CAMetalLayer` itself and is set to `bra8Unorm`.

`bgra8Unorm` is an 8 bit unsigned int color format. All the 4 components (B, G, R, A) are 8 bits long each and hence the total length is 32 bits. Unorm means any component's value can be between 0 and 255.

###### MTLCommandQueue, MTLCommandBuffer -

To submit any work to GPU, command queues need to be used. The work instructions are actually contained in command buffers, they included encoded render commands. Command queues contain command buffers. In fact, the command queue is just a serial queue that dispatches work to GPU in an organized manner.

Command queues are a thread safe way of submitting work to GPU. What it means is that commands can be submitted to GPU though multiple command queues at the same time. It isn't that what has been submitted from queue1, can be unexpectedly corrupted by what gets submitted from queue2.

The command queue is created from the metal device. And they are expensive to create, so should be created frugally. The command queue then creates command buffer.

```
commandQueue = metalDevice.makeCommandQueue()
commandBuffer = commandQueue.makeCommandBuffer()
```

The command buffer then creates an encoder object to fill the buffer with commands.
Technically both `MTLCommandQueue`, `MTLCommandBuffer` are protocols 

Command buffer's `present()` method is what actually declares the intent to present the command buffer's drawable presented to the screen. And eventually a commit needs to done on the command buffer to commit all the commands to the GPU through the command queue.

Once a command buffer is encoded, no further commands can be added into it (but the encoding happens on render command encoder right?).

###### MTLRenderCommandEncoder -

It contains the rendering commands. The vertex buffer, render pass descriptor as well as the render pipeline state get attached to it.
Its `drawPrimitives` method is how the drawCalls actually get issued to GPU. I mean technically, not right away but whenever GPU comes to it through the queue of submitted commands.

```
guard let renderEncoder = commandBuffer.makeRenderCommandEncoder(descriptor: renderPassDescriptor) else { return }

renderEncoder.setRenderPipelineState(pipelineState)
renderEncoder.setVertexBuffer(vertexBuffer, offset: 0, index: 0)
renderEncoder.drawPrimitives(type: .triangle, vertexStart: 0, vertexCount: 3)
renderEncoder.endEncoding()

commandBuffer.present(drawable)
commandBuffer.commit()

The presentation should be done in an autorelease pool (why, isn't ARC at work?).

autoreleasepool {
    self.renderToScreen() // All the present() and commit() code
}
```

###### MTLBuffer -

It represents a buffer, i.e. memory alocation that can be accessed by the GPU. Its created using makeBuffer(bytes:length:options:) method.

For `makeBuffer(bytes:length:options:)``, the first argument is an `UnsafeRawPointer`` that specifies the memory address from which to copy the initial data, the second argument is the entire allocation's length and the third argument are the options. The specified options can be `storageModeShared` or `storageModeManagedShared` but should not be `storageModePrivate`.

```
let vertices: [Float] = [0.0, 0.5, 0.0,
                         -1.0, -0.5, 0.0,
                         1.0, -0.5, 0.0]


let dataSize = vertices.count * MemoryLayout.size(ofValue: vertices[0])
vertexBuffer = metalDevice.makeBuffer(bytes: vertices, length: dataSize, options: .storageModeShared)
```

The method makes a 'buffer', which in pointer terms should mean strideable memory (i.e. an array like thing).

Typically vertices data is represented as a `MTLBuffer` and is called vertex buffer.
Keep in mind that multiple buffers can be created and attached to the render command encoder. All these buffers then become available to the vertex shader.

`MTLBuffer` too is a protocol and a custom class that conforms to it should not be created.

###### MTLLibrary and MTLFunction -

The shaders are put in a .metal file. And a library (`MTLLibrary`) containing all these functions are made available by `MTLDevice`'s `makeDefaultLibrary` function. The individual functions are then made available as `MTLFunction` by the library's `makeFunction(name:)` method. These metal functions are then tied to the render pipeline descriptor.

```
guard let metalLibrary = metalDevice.makeDefaultLibrary(),
    let vertexMetalFunction = metalLibrary.makeFunction(name: "basic_vertex"),
    let fragmentMetalFunction = metalLibrary.makeFunction(name: "basic_fragment")
    else { return }

let pipelineStateDescriptor = MTLRenderPipelineDescriptor()
pipelineStateDescriptor.vertexFunction = vertexMetalFunction
pipelineStateDescriptor.fragmentFunction = fragmentMetalFunction
```

So `MTLLibrary` is just a library containing all the shader source code in the project. `MTLFunction` represents a shader function (the possible types are vertex, fragment and also something called compute or kernel).

###### MTLVertexDescriptor -

It is something that tells how the vertices data is organized and mapped to the vertex shader. In context of Metal, a `vertexDescriptor` property is configured on the render pipeline descriptor, which tells how the vertex data is specified in the argument table (i.e. the vertex buffer). So it seems that this property has a bearing on the order of arguments passed(and also what they mean) to the vertex shader. It has things such as what the format of each attribute is (float4, etc.), offset, etc.

###### Misc. -

Remember, API wise render pass and render pipeline are different things. Pipelines are a pre-compiled set of graphics state and include the shader functions. They are expensive to create. Usually you create one render pipeline descriptor for every distinct pair of vertex and fragment shaders.
