How undo and redo work.

NSUndoManager is a general purpose undo stack where clients can register callbacks to be invoked should an undo be requested. While performing an undo, the undo manager saves the operations that get undone so that redo can be done.

While registering an undo operation, following things can be specified - the object to receive the message, the message to send, the arguments to be passed. Typically at least one argument, i.e. the original value needs to be passed.

Also the invoked method should usually save the previous value which can then be used for redo (it does not happen automatically?).

Undo operations are typically collected in undo groups which are all performed together when an undo or redo is requested.

Undo groups are stored in stacks which are unlimited by default. However, a limit can be set on the no. of groups and if its exceeded the oldest group gets removed from the stack.

Redo stack remains empty until undo is performed. Consecutive undos add to the redo stack. Subsequent redo operations pull the operations off the redo stack, apply them to the objects and push appropriate operations back onto the undo stack. However, the contents in a redo stack do not stay forever. When a new undo operation is registered, the existing redo stack gets cleared. Just keep this thumb rule in mind.

Usually a single instance of NSUndoManager belongs to an object that contains other objects. This object is known as the undo manager’s client. However, it can also be so designed that an object that is changed has its own undo manager and performs its own undo and redo operations.
