While creating a relationship, the following things need to be specified for it -
1. Name
2. Destination
3. Cardinality, i.e. is it to-one or to-many
4. Inverse relationship
5. Delete Rule
6. Optionality
7. Minimum and maximum count

Reflexive relationship is one where the destination entity of relationship is the same entity as the source. A many-many relationship is one where a relationship as well as its inverse are both to-many. 

If a relationship is not optional, then for it to be valid there must be an object or objects at the destination of the relationship.

Apart from in the case of fetched properties, it is always recommended to have an inverse relationship for a relationship.

A relationship's delete rule specifies what happens when an attempt is made to delete a source object. There can be following delete rules -
1. Deny - If there is even one object at destination, the source object's deletion is not allowed. The managed objects at the destination of relationship must be deleted before deleting the managed object in question
2. Nullify - The inverse relationship is set to null. So the destination object knows that it doesn't anymore have objects at the other end (i.e. its destination) of the relationship.
3. Cascade - The destination objects also get deleted.
4. No Action - Nothing happens at destination end. The source object is deleted and the destination object does not even know that the source object does not exist any more. (Not recommended to use.)

A unidirectional relationship is one which does not have an inverse relationship. 
Usually such a scenario may not be needed, but if it is needed it is possible. However, in such a case the object graph integrity has to be maintained specifically in the code. It will not happen automatically. Hence, it is generally not recommended to have unidirectional relationships.

Fetched properties are useful when an entity needs to have a relationship with another entity that does not belong to the same store. They are like relationships but are not quite relationships. At the same time, they are a bit like properties but are not exactly properties either. It is best to think of them as properties which behave like relationships, unidirectional relationships whose destination entity can even be in a different store. Their values are fetched using a fetch request and the results are always returned as an array as per the sort order specified in the fetch request. Also, the values it fetches or has are not dynamic. Once the values have been fetched once, to get the latest values again refreshObject:mergeChanges: needs to be called for the managed object to which it belongs. A fetched property's predicate has two special variables -
1. $FETCH_SOURCE - Refers to the managed object (i.e. the source side of the 'relationship') that has this fetched property
2. $FETCHED_PROPERTY - Refers to a description of this fetched property. It has a userInfo dictionary which can be populated with key-value pairs that can be used to store any thing as may be needed.
The corresponding class for fetched properties is NSFetchedProperty. It has just 2 instance methods, -fetchRequest and -setFetchRequest:. (Then where is the userInfo dictionary of fetched property present?)

Faults reduce the memory consumed by the application, as they help to reduce the size of the object graph. It is a placeholder object that represents a managed object or a collection object (such as NSSet in case of a to-many relationship) that has not yet been fully realized. Without faults, to even load a single managed object all the objects that are connected to it using any relationship (directly or indirectly) would have been required to be loaded. Hence, faults are immense in terms of reducing the object graph size.
When a fault is fired, Core Data does not necessarily go to the store. If the data is available in cache, it gets it from the cache and it is much faster. Whether or not an object is fault can be checked by sending it a isFault message. If it returns NO, then of course it is not a fault and is fully realized. However, if it returns YES it does not mean that the object is not in memory as it may still be in the cache. It just implies that the object is currently a fault and the fault needs to be fired to get its values.

Sometimes it is helpful to turn a realized object into fault, as it can greatly reduce the size of the object graph. A realized object can be turned into a fault by passing it in the refreshObject:mergeChanges: method and specifying the mergeChanges flag as NO. However, in doing so it must be ensured that there are no changes to the object's relationships as then saving the context may throw referrential integrity errors.
When Core Data turns an object into a fault, KVO notifications are sent for the obect's properties. Now, there is an oddity here. If the object turns into a fault and the fault is subsequently realized, the change notifications are sent for the properties whose values did not in fact change. (And also for the properties whose values did change, right?)


When a context is saved to persistent store, the possible conflicts in saving that data due to changes that might have been done by another context are detected using a mechanism called Optimistic Locking. The way these conflicts are resolved depend upon how the context has been configured.

When objects are fetched from the persistent store, Core Data takes a snapshot of its state, i.e. a dictionary of the object's persistent properties. When a context save is later on attempted, it is first checked if there are any differences between the last taken snapshot and the current values in the persistent store for those objects. If there are no differences, it implies that no other context has made a save in the meantime for those records and hence there is no conflict. In such a case, the save proceeds normally and the snapshot is also updated with the latest values. If however there is a difference between the snapshot and the current values in the store, there is an optimistic locking 'failure' (i.e. there is a conflict).

The behaviour of a context when it encounters an optimistic locking failure is specified in the mergePolicy property. It is of the enum type NSMergePolicyType and has the following possible values -
1. NSErrorMergePolicyType (Save will fail and generate an error)
2. NSMergeByPropertyStoreTrumpMergePolicyType (Data is merged and if a property is different in both, the one in the store wins)
3. NSMergeByPropertyObjectTrumpMergePolicyType (Data is merged and if a property is different in both, the one in the context wins)
4. NSOverwriteMergePolicyType (Entire in-memory objects will be overwritten upon the values in persistent store)
5. NSRollbackMergePolicyType (In-memory changes will be discarded and the values in persistent store retained)

If there are more than one managed object contexts in an application, changes in one can be informed to the other if the other context registers for the NSManagedObjectContextDidSave notification. The notification contains information about the changed objects as well as deleted objects.

Core Data ensures that in a given managed objct context, an entry in a persistent store is associated with only one managed object. This is known as uniquing.
It is possible to migrate a persistent store from one location to another using -migratePersistentStore:toURL:options:withType:error: method. In doing so, the persistent store type can also be specified to be changed (i.e. XML store to SQLite store, etc.). Now one thing to note is that while migrating the objects to the new persistent store the object IDs also get changed.

Metadata (which is nothing but a dictionary) can be associated with a store, so that it can be indexed by Spotlight. The metadata can have custom keys or one of the standard set of Spotlight keys. Some of the methods for accessing the metadata of a store are NSPersistentStoreCoordinator class method metadataForPersistentStoreWithURL:error and NSPersistentStore class method metadataForPersistentStoreWithURL:error.
