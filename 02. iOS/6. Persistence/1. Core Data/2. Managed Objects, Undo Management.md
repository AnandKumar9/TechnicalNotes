Whether an object has been deleted from the store or not can be checked by executing a fetch request and having a predicate of the form 'self == %@', where the managed object or the managed object ID is passed as the parameter.    

When a super entity is specified as the entity for a fetch request, the request returns all matching instances of the super entity as well as sub entity. (May not be so, will need to check. It will certainly include the objects corresponding to super entity that have been created while creating the sub entity. But it should not include the instances corresponding to sub entity when the fetch request has been done for the super entity.)

resultType property of fetchRequest can also be used to fetch data a little differently than retrieving full managed objects. Here are the possible values.

1. The default result type is `NSManagedObjectResultType`. It returns the entire managed object.

2. `NSManagedObjectIDResultType` returns just the managed object IDs. So you cannot just simply access the managed object's properties through it. Instead you can access the `NSManagedObjectID` properties.

3. `NSDictionaryResultTypes` returns dictionaries in each of the elements in the returned array. Every dictionary contains only the properties (or relationships or expressions) specified in the propertiesToFetch. Hence, it is useful when not all the properties of the qualifying managed objects need to be fetched. By default, I think all the properties are included. If a relationship's property is needed, the full key path of that property should be given. For example, state.name where state is a relationship. Just giving the relationship's name does not help to later get the relationship's property as it was not even fetched and this fault for some reason cannot be fired. Also, it's important to note that the elements specified in propertiesToFetch array need not just be properties or relationships, they can also be expressions.

4. `NSCountResultType` returns just one element in the array and it is a NSNumber having just the count of the qualifying managed objects. Thats all, nothing else is returned. So its very efficient when just a count of qualifying objects needs to be fetched.

To fetch only the unique values of a particular attribute, returnsDistinctResults can be specified as YES, the return type should be NSDictionaryResultType and that attribute should be the only attribute specified in propertiesToFetch. This attribute can even be an attribute at the other end of a relationship, in which case it can be specified with the dot notation in propertiesToFetch.

fetchLimit can be used to specify how many results must be fetched and fetchOffset can be used to specify the offset (i.e. no. of qualifying matches to be skipped) to be applied while fetching the results. Both of these are applied after the sort descriptors have been applied.

fetchBatchSize specifies the no. of results to be included in one batch. The returned array still gives the complete count, but only a part is loaded from persistent store at a time, remaining data is loaded automatically as needed. However, this probably comes into play only when working with fetched results controller and with a huge data set of thousands of records. For a very small data set, this does not seem to make any difference and all the records were still completely loaded.

In case a specific attribute value needs to be fetched which satisfies a condition, such as maximum across all managed objects or minimum across all managed objects, it can be done by creating a the appropriate expression descriptions and assigning them as the propertiesToFetch. Every expression description needs to be given a unique name and an expression which says what expression needs to be applied on what property (key path). The results array returned by the fetch request has just one element which is a dictionary with a key for each of the passed expression descriptions and the value being the corresponding attribute value.
([link](https://useyourloaf.com/blog/2012/01/19/core-data-queries-using-expressions.html), test project - 3. Core Data - FetchRequest Result Type/TestVarious)

A to-many relationship is represented using a NSSet.
The to-many relationship in a managed object can be edited using the Core Data generated accessor methods add<Key>Object, etc. as well as the KVC method mutableSetValue:forKey:. Using mutableSetValue:forKey: returns a mutable proxy object and changing it ensures that the KVO notifications are also fired. However, when using dot notations (which in turn uses the default generated Core Data accessor methods) just a set is returned and the KVO notifications are not fired, also the inverse relationship is not updated correctly (why?).

A NSManagedObjectID is a universal identifier for a managed object. It uniquely identifies the same managed object between contexts in same application as well as multiple applications (in case of distributed systems).

There are 2 forms of an object ID. When a managed object is created, it is assigned a temporary ID and then when it is saved, it is assigned a permanent ID.
In addition to the object ID, a unique URI representation of a managed object can also be shown with the same effect as that of an object ID.

Core Data provides automatic support for Undo Management. It is supported even for transient properties. Each managed object context maintains an undo manager. There are some methods in NSManagedObjectContext that together provide the undo and redo support (-undo, -redo, -rollback, etc.). Doing a rollback rolls back all the changes since last save operation and also clears the undo stack. Doing a reset however, goes one step ahead and removes all the managed objects (even the ones initially fetched from the store when the context was created) from the context. They aren't deleted from the store but wiped out from the context.

Fault is an object whose property value have not yet fully loaded from the external store. When a managed object is fetched, Core Data does not automatically fetch data for other objects to which that has object has relationships. Hence, initially an object's relationships are represented by faults. However when the relationship's destination data is accessed, the fault fires and the data is automatically retrieved.

If the same data store is being used by two different contexts and the same set of records have been fetched by both, both the contexts hold the values that were last fetched. If in between the values are changed in data store by one context (and saved?), it will not be automatically reflected in the other context. To get the latest value, refreshObject:mergeChanges: method of NSManagedObjectContext needs to be invoked with the managed object passed to it and the mergeChanges flag set as YES. If the mergeChanges flag is set as NO, the object is turned into a fault without merging, which is useful in reducing the size of the object graph.

If mergeChanges flag is set as YES, the managed object's property values are reloaded from the store or the last cached state and then the changes made in the local context are applied over them. If it is set as NO, the changes made in the local context are not applied.

While making a fetch request by default the objects are returned as fault, i.e. the relationships data is not fetched right away. This can be verified by printing the returned array in debug console. Any relationship which has not yet been accessed by the code (or even in the debug session) is shown as a fault. This can be changed by setting returnsObjectsAsFaults property of the fetch request to NO in which case all the objects are returned completely and not as faults. This is particularly useful when you would need to access the relationships for all the objects anyway after fetching as then there will be an overhead of the fault needs to be fired every time.
