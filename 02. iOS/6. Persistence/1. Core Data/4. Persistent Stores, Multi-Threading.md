Core Data allows to have three different types of disk-based persistent stores - XML, atomic, SQLite and another in-memory store (which is not same as 'in memory data' that has been referred to so far, that is probably a different thing). From the application code perspective, it usually does not matter what kind of a store the app is using as the code interacts just with stack and managed objects. However, there are some basic things about different stores that should be kept in mind.

XML stores are human-readable, but are slower and bring the entire store to the object graph.

Atomic stores are fast but bring the entire store to the object graph.
SQLite stores are fast and can be limited to bring the necessary records to the object graph, but are not quite human-readable as when used with Core Data, SQLite store format is private.

In XML, atomic and in-memory stores, evaluation of predicates and sort descriptors is done in Objective-C with access to all of Cocoa's functionalities including the comparison methods on NSString. However with the SQLite store, predicates and sort descriptors are compiled to SQL and the result is evaluated in the database itself. Hence, sort descriptors or predicates that rely on Cocoa alone do not work.

With SQLite stores, sorting cannot be done based on transient properties.
Core Data cannot give any gurantee about the security of persistent stores from untrusted sources and cannot detect whether files have been maliciously modified.

There are some interactions between fetching and the type of store. In the XML, binary, and in-memory stores, evaluation of the predicate and sort descriptors is performed in Objective-C with access to all Cocoa's functionality, including the comparison methods on NSString. The SQL store on the other hand, compiles the predicate and sort descriptors to SQL and evaluates the result in the database itself. This is done primarily for performance, but it means that evaluation happens in a non-Cocoa environment, and so sort descriptors (or predicates) that rely on Cocoa cannot work. The supported sort selectors are compare: and caseInsensitiveCompare:, localizedCompare:, localizedCaseInsensitiveCompare:, and localizedStandardCompare: (the latter is Finder-like sorting, and what most people should use most of the time). In addition you cannot sort on transient properties using the SQLite store.

Core Data provides a way to control sync behavior for SQLite stores which give some control over the trade-off between performance and reliability.
'synchronous' controls the frequency of disc syncing, 'full_fsync' controls the type of disk-sync operation performed. They can be set using NSSQLitePragmasOption key in the options dictionary which is passed when opening the persistent store (by adding it to the coordinator).

One of the common multi-threading techniques used in Core Data is to execute a fetch request in a background thread when there is a SQLite persistent store and there are a very high no. of records to be fetched. In such case, you fetch in managed object context on a background thread and pass the object IDs of the fetched objects to another thread (typically the application's main thread).

If there is a need to merge changes done by save in a separate context with the current context, then mergeChangesFromContextDidSaveNotification: method can also be called on the current context. This method needs the NSManagedObjectContextDidSaveNotification (which is posted when the save is done on the other context) to be passed as an argument and hence should be called when a NSManagedObjectContextDidSaveNotification for the other context is received.

When using multiple threads with Core Data, special care must be taken to ensure that the object graph never enters an inconsistent state. It isn't the case with Core Data that reads are always harmless as even reads may be firing faults. Managed objects themselves are not thread safe and it is not a good practise to work with the same managed objects across threads. If at all managed objects need to be passed between threads, it is their objectIDs that should be passed instead and then objectWithID: should be used in the receiving thread's context to get a local version of the managed object. Also, the corresponding managed objects must have been saved, objectID of newly inserted managed objects cannot be passed to another context.

The safest approach is to have a separate context for each thread and share a single coordinator across them. The next recommended approach is to have a separate context as well as coordinator for each thread. This is needed when each thread needs to do completely concurrent operations. What is not at all encouraged is to pass managed objects or contexts between threads. If at all this approach is taken, appropriate locks must be applied and a lot of care taken to ensure that the object graph is not entering an inconsistent state.

Performing a save operation in a detached thread (all NSThread-based threads are detached) is error-prone and additional steps must be taken to ensure that application is explicitly prevented from quitting before the save is completed.

iOS5 onwards the concept of parent-child contexts has been introduced. A context can be set up as a child context of another context. Whenever a save is done on the child context, the changes are pushed to the parent context but not to the store yet. Then when a save is done on the parent context, the changes are finally pushed to the store. This is especially useful for save and cancel kind of situations where a save should push the change, but a cancel should rollback the changes and additionally there might be multiple such streams needed. A context is set as the child of another context by calling the method setParentContext:. Then the parent context observes the child context for NSManagedObjectContextDidSaveNotification and then finally does a save itself when it does receive the notification. Also, the child context can be initialized using initWithConcurrencyType: method with a concurrency type specified. The most common concurrency type used is NSMainQueueConcurrencyType which implies that the context will be associated with the main queue.
