#### What is IndexedDB

`IndexedDB` is a database that is built into a browser that is much more powerful than what any of the web storage objects work with.

It stores almost any kind of values by keys, multiple key types.
It supports transactions for reliability. ?
It supports key range queries, indexes. ?
It can store much bigger volumes of data than localStorage.

`IndexedDB` is intended for offline apps, to be combined with ServiceWorkers ([this](https://developer.chrome.com/docs/workbox/service-worker-overview/) thing?) and other technologies.

The native [interface](https://www.w3.org/TR/IndexedDB) to IndexedDB is event-based. There is also an async-await promise-based wrapper named [idb](https://github.com/jakearchibald/idb) that exists.

> Technically, the data is usually stored in the visitor’s home directory, along with browser settings, extensions, etc. Different browsers and OS-level users have each their own independant storage.

#### Opening a database connection

```
let openRequest = indexedDB.open(name, version);

openRequest.onupgradeneeded = function() {
  // triggers if the client had no database
  // ...perform initialization...
};

openRequest.onerror = function() {
  console.error("Error", openRequest.error);
};

openRequest.onsuccess = function() {
  let db = openRequest.result;
  // continue working with database using db object
};
```

`name` is the database name, `version` by default is 1.

The call returns `openRequest` object, we should listen to events on it.

`success`: database is ready, there’s the “database object” in openRequest.result, we should use it for further calls.
`error`: opening failed.
`upgradeneeded`: database is ready, but its version is outdated (see below).

> If the local database version is less than specified in `open`, then a special event `upgradeneeded` is triggered, and we can compare versions and upgrade data structures as needed. The `upgradeneeded` event also triggers when the database doesn’t yet exist (technically, its version is `0`), so we can perform the initialization.

##### Deleting a database

```
let deleteRequest = indexedDB.deleteDatabase(name)
// deleteRequest.onsuccess/onerror tracks the result
```

##### Handling parallel update

Its possible that when a webpage is accessed in one tab it has one version of the database, and subsequently when the webpage is also opened in another tab it the page now uses a new version of the database. In such a case, `onversionchange` event triggers an outdated database object and it should be handled.

```
let openRequest = indexedDB.open("store", 2);

openRequest.onupgradeneeded = ...;
openRequest.onerror = ...;

openRequest.onsuccess = function() {
  let db = openRequest.result;

  db.onversionchange = function() {
    db.close();
    alert("Database is outdated, please reload the page.")
  };

  // ...the db is ready, use it...
};

openRequest.onblocked = function() {
  // this event shouldn't trigger if we handle onversionchange correctly

  // it means that there's another open connection to the same database
  // and it wasn't closed after db.onversionchange triggered for it
};
```



#### Object store

An `Object Store` is needed to store things in `IndexedDB`, conceptually its nothing but a table. There must be a unique key in every store.

WWhen we store objects, IndexedDB even allows setting up an object property as the key, which is much more convenient. Or we can auto-generate keys.

Creating an object store. It is synchronous and no `await` is needed.

```
db.createObjectStore(name[, keyOptions]);
```

An object store can only be created/modified while updating the DB version, in `upgradeneeded` handler.

Deleting an object store.

```
db.deleteObjectStore('books')
```

#### Transactions

All data updates in IndexedDB need to be wrapped in something known as a `Transaction`.

Starting a transaction. `store` is a store name that the transaction is going to access. Can be an array of store names if we’re going to access multiple stores. `type` denotes a transaction type, it can be `readonly` or `readwrite` (can only read and write the data, but not create/remove/alter object stores).

```
db.transaction(store[, type])
```

>  There’s also `versionchange` transaction type: such transactions can do everything, but we can’t create them manually.

Adding an item to the store.

```
let transaction = db.transaction("books", "readwrite"); // (1)

// get an object store to operate on it
let books = transaction.objectStore("books"); // (2)

let book = {
  id: 'js',
  price: 10,
  created: new Date()
};

let request = books.add(book); // (3)

request.onsuccess = function() { // (4)
  console.log("Book added to the store", request.result);
  
};

request.onerror = function() {
  console.log("Error", request.error);
};
```

Object stores support two methods to store a value - `put(value, [key])`, `add(value, [key])`.

#### Transactions' autocommit

When all transaction requests are finished, and the [microtasks queue](https://javascript.info/microtask-queue) is empty, it is committed automatically. As of mid-2023, there is no way to manually mark a transaction as finished with no more tasks pending.

Transactions auto-commit principle has an important side effect. We can’t insert an async operation like fetch, setTimeout in the middle of a transaction. IndexedDB will not keep the transaction waiting till these are done. In the code below request2 fails, because fetch is an asynchronous operation, a macrotask. Transactions are closed before the browser starts doing macrotasks.

```
let request1 = books.add(book);

request1.onsuccess = function() {
  fetch('/').then(response => {
    let request2 = books.add(anotherBook); // (*)
    request2.onerror = function() {
      console.log(request2.error.name); // TransactionInactiveError
    };
  });
};
```

#### Error handling

Write requests may fail. In some situations, we may want to handle the failure (e.g. try another request), without canceling existing changes, and continue the transaction. The `request.onerror` handler can do that by calling `event.preventDefault`.

#### Event delegation

If every request's onerror/onsuccess need not be written, event delegation can be used.

IndexedDB events bubble: request → transaction → database.

All events are DOM events, with capturing and bubbling, but usually only bubbling stage is used

(JavaScript.info [link](https://javascript.info/indexeddb#event-delegation))

#### Cursors

A cursor is a special object that traverses the object storage, given a query, and returns one key/value at a time, thus saving memory.

```
let transaction = db.transaction("books");
let books = transaction.objectStore("books");

let request = books.openCursor();

// called for each book found by the cursor
request.onsuccess = function() {
  let cursor = request.result;
  if (cursor) {
    let key = cursor.key; // book key (id field)
    let value = cursor.value; // book object
    console.log(key, value);
    cursor.continue();
  } else {
    console.log("No more books");
  }
};
```

The main cursor methods are `advance(count)` and `continue([key])`.

#### Promise wrapper

Adding onsuccess/onerror to every request is quite a cumbersome task. Sometimes we can make our life easier by using event delegation, e.g. set handlers on the whole transactions, but async/await is much more convenient. ([link](https://javascript.info/indexeddb#promise-wrapper))
