#### What is a process

A process is a UNIX abstraction that lets files and programs be looked at in another way. A file is treated as a simple file when it lies in a dormant state on disk. And then it can also be thought of as a process when it is executed.

A process is simply an instance of a running program. It's however not the same thing as a program. When two users run the same program, there is one program on disk but two processes in memory.

Process belongs to the domain of kernel, which is responsible for their management. The kernel sometimes even has to store pages (sections) of these processes in swap area of the disk before calling them again for running. All this happens several times in a second, thereby making the suer oblivious to the switching process.

#### Getting a list of all processes and their attributes (`ps`)

The attributes of a process are maintained by kernel in a separate structure called the `process table`. It can be thought of as inode for processes. There are two important attributes of a process.

`Process-id (PID)` - A unique integer allotted by kernel to a process when its born <br>
`Parent PID (PPID)` <br>

When you login, a process is immediately set up by the kernel, and it remains alive until you log out. This process represents a UNIX command which may be `sh`, `ksh`, `csh`, or `bash`. The PID of the current shell process is stored in a separate variable that can be accessed by `$$`.
```
Desktop (11:16 PM) $ ps
  PID TTY           TIME CMD
11077 ttys000    0:00.15 -bash

Desktop (11:16 PM) $ echo $$
11077
```

The ancestry of every process can be ultimately traced to the first process (PID 0) that is set up when the system is booted.

By default, `ps` displays the processes owned by the user running the command.
```
Desktop (09:16 PM) $ ps
  PID TTY           TIME CMD
11077 ttys000    0:00.26 -bash
50993 ttys001    0:00.05 -bash
51056 ttys002    0:00.06 -bash

Desktop (09:16 PM) $ echo $$
11077
```

`TIME` is the cumulative processor time that has been consumed since the process has been started. `CMD` is the process name (why is it always bash?). `TTY` gives the terminal with which the process is associated.

`-f` shows more attributes including `PPID`. `STIME` shows the time the process started. `CMD` shows the entire command line with its arguments. So apparently if some long running process has been started using a command, the entire command should get shown here.
```
Desktop (09:16 PM) $ ps -f
  UID   PID  PPID   C STIME   TTY           TIME CMD
  503 11077 11076   0 10:48PM ttys000    0:00.26 -bash
  503 50993 50992   0  9:16PM ttys001    0:00.05 -bash
  503 51056 51055   0  9:16PM ttys002    0:00.06 -bash
```
`-e` or `-A` show all processes including user and system processes.

`-u` shows the processes of a specific user.

`-l` shows more of memory related information.
```
Desktop (10:00 PM) $ ps -l
  UID   PID  PPID        F CPU PRI NI       SZ    RSS WCHAN     S             ADDR TTY           TIME CMD
  503 11077 11076     4006   0  31  0  4467536   2632 -      S                   0 ttys000    0:00.27 -bash
  503 50993 50992     4006   0  31  0  4595536   3620 -      S+                  0 ttys001    0:00.05 -bash
  503 51056 51055     4006   0  31  0  4581200   3740 -      S+                  0 ttys002    0:00.06 -bash
```

###### System process or Daemons

Apart from the processes a user generates, a number of system processes keep running all the time. Most of them are not associated with any terminal. `System processes` are easily identified with a `?` in their `TTY` columns. This also means that their standard input and standard output are not connected to the terminal. Such processes can hence not be interrupted using Ctrl + C either.
These processes are known as `daemons`. Most of them are usually sleeping and wake up only when they receive input.

For example, `lpsched` daemon controls all printing activity, `sendmail` daemon handles the incoming and outgoing mail. `inetd` daemon controls the TCP/IP network's FTP and TELNET.

Many system daemons in fact act as server components of a TCP/IP network. They listen at certain ports for user requests and then wake up when they receive input. For each of these daemons, there is usually a corresponding client component as well on another machine. For example, the `ftp` command on the client machine communicates with the `inetd` daemon on the server.

#### Mechanism of process creation

There are three different system calls that happen during the process creation cycle.

`fork` Creates copy of the process that invokes it (i.e. the process that asks for a new process to be create). The process image is quite similar to that of calling process, but does get a new `PID` of its own.

`exec` With this, the forked child overwrites its own image with code and data of new program.

`wait` The parent then executes this to wait for child process to complete. It picks up the exit status of the child and then continues with its other functions. However, it's possible to instruct parent to not wait for that.

Here are some of the attributes that a child process inherits verbatim from its parent. <br>
Real `UID` and `GID` of the process, which actually indicate the `UID` and `GID` of user running the program. These parameters are stored for the user in `/etc/passwd`. <br>
Current directory where the process was run. This is also the reason that you can't create a process to change your current directory. <br>
Effective `UID` and `GID` of the process which are usually the same for the 'real' cousins. <br>
Environment variables like `HOME` and `PATH`. <br>

One user cannot terminate or control the process created by another user, but the root user can.

#### Command classification with respect to processes

From a process viewpoint, there are 3 types of commands.

`External commands` These are `cat`, `ls`, etc. Shell creates a process for each of these commands that it executes while remaining their parent.

`Shell scripts` The shell executes these scripts by spawning another shell, which then executes the commands listed in the script. The child shell becomes parent of the commands that feature in the script.

`Internal commands` These are `cd`, `echo`, etc. A new process is not generated for some of them and are executed directly by the shell.

#### Process states and zombies

After creation a process is in `runnable` state until when it actually starts running. While running if it invokes something else (like a disk I/O operation), it needs to just wait idly for that operation to get over, and enters a `sleeping` state during that time.  A process can also be `suspended` by pressing an interrupt key. Processes whose parents do not wait for termination move to `zombie` state. A process also enters `zombie` state when it's terminated and remains in that state until its parent picks up its exit status from the process table.

#### Running jobs in background

There can be only one job in foreground at a time, remaining jobs can only be in background. There are 2 ways to run a job in background.

###### `&` (No logging out)

If a command is suffixed with `&`, the parent does not wait for it to finish. It immediately creates a process for the enters command, prints its `PID`, returns the prompt and becomes ready to accept another command. The actual command gets run in the background in the meantime.

```
Projects (09:19 PM) $ ls -l &
[1] 74542

Projects (11:26 PM) $ total 16
drwxrwxr--@  5 sou543  staff   160 Jul 26 06:28 1.Ease
drwxrwxr--@ 15 sou543  staff   480 Jul 26 08:12 2.Eno
drwxrwxr--@ 14 sou543  staff   448 Aug 29 14:42 3.PayPal
drwxrwxr--@  8 sou543  staff   256 Aug 13 19:20 4.SpendingToggle
drwxrwxr--@  8 sou543  staff   256 Sep  6 12:26 5.PostLSRP
drwxrwxr--@  6 sou543  staff   192 Jul 29 10:35 6.DesktopSafari
drwxr-xr-x   7 sou543  staff   224 Sep  5 11:27 7.ApplePay
drwxr-xr-x   5 sou543  staff   160 Aug 22 17:23 8.VirtualCardManager
-rw-r--r--@  1 sou543  staff  2050 Sep 18 20:15 All APIs.txt
drwxrwxr--@  8 sou543  staff   256 Jul 26 06:37 Files
-rw-rw-r--@  1 sou543  staff   325 Jul  2 18:46 Test accounts.txt
```

###### `nohup` (Log out safely)

Background jobs cease to run if user logs out or parent shell is terminated for any reason. This behavior can be altered by specifying `nohup` as prefix and `&` as suffix. The output of the command though gets redirected to the file `nohup.out` though.

```
Projects (11:26 PM) $ nohup ls -l &
[1] 74563

Projects (11:32 PM) $ cat -b nohup.out
     1	total 16
     2	drwxrwxr--@  5 sou543  staff   160 Jul 26 06:28 1.Ease
     3	drwxrwxr--@ 15 sou543  staff   480 Jul 26 08:12 2.Eno
````

> It's written in the book that if a pipeline has more than one commands, they all should use `nohup &`. Why? Can they not use `&` at all and actually wait for every command to finish. I think that works.

By default all processes run with equal priority. `nice` command can be used to specify a low priority for the job.

`nice wc -l SomeFile` - Runs with low priority <br>
`nice -n 5 wc -l SomeFile` - `-n` fine tunes the priority. 1 to 20 is allowed with 20 being least possible priority.

*****

Signals indicate the occurrence of an event to processes. Each signal has a number, but they differ from system to system and are hence instead identified using names. Pressing interrupt key sends `SIGINT` signal. A process can have its own custom action for all signals other than `SIGKILL` and `SIGSTOP`, their default action always runs and terminates the process.

`kill` command sends a signal, usually with the intention of terminating one or more processes.

The below command terminates the processES with PID '105' and '232'.
```
kill 105 232
```

In most systems, `$!` has the PID of the last background job. So `kill $!` can stop the latest background job.

#### Jobs

A job is the name given to a group of processes. The simplest way to create a job is to create a pipeline of commands.

There are some job control facilities to manage long running jobs.

###### Moving to background (`bg`) or foreground (`fg`)

`Ctrl + Z` suspends a foreground job.

A job can be relegated to background with `bg`.
```
~ (11:52 PM) $ find . -name "*png" -print
./.atom/packages/atom-beautify/node_modules/mute-stream/coverage/lcov-report/sort-arrow-sprite.png
./.atom/packages/atom-beautify/node_modules/colors/screenshots/colors.png

#### PRESSED CONTROL + Z TO SUSPEND THE JOB
^Z
[1]+  Stopped                 find . -name "*png" -print

~ (11:54 PM) $ bg

#### THE JOB CONTINUES IN BACKGROUND
```

Similarly a job can be moved back to foreground with `fg`.
```
fg %1  - Brings first job to foreground
gf %sort    - Brings sort job to foreground
```

###### Listing all jobs

`jobs` lists all the active jobs.

#### Scheduling jobs

###### Scheduling for later (`at` and `batch`)

`at` allows to have a specific time at which to run a job.

```
$ at 14:08
> somescript.sh
### Ctrl + D
$
```

It also keywords like 'noon', 'tomorrow', etc. Jobs can be listed with `at -l`, and removed with `at -r`.

`batch` too schedules jobs, but instead of asking for a specific time it also allows them to run as soon as the system load permits.
```
$ batch < somescript.sh
```

###### Running periodically (`cron` daemon and `crontab` command)

`cron` is a daemon that is always running. It is mostly dormant but every minute it wakes up and looks in a specific file (called the `crontab` file) for instructions to be performed.
The `crontab` command allows to place a custom crontab file in the place where `cron` periodically looks for crontab files.
```
crontab newcrontab.txt
```

`crontab -l` shows the content of your current crontab file, and `crontab -r` removes it.

There is also another custom utility called `watch` which can be used very easily to run a command or script at regular intervals. It can be installed via `homebrew`. In the below example, the script is run every 2 sec.
```
watch -n 2 /Users/sou543/Desktop/LogTime.s
```

###### Measuring time taken by a process (`time`)

`time` command gives the metrics regarding how long it took to run a command.
```
$ time find . -name "*PayPal*" -print
./Enterprise Tests/MobileUI/Features/PayPal/PayPalAgreeViewControllerTests.swift
./Enterprise Tests/MobileUI/Features/PayPal/PayPalRouterTests.swift

real	0m0.792s
user	0m0.132s
sys	0m0.659s
```

`real` is the actual time between command invocation and termination. `user` is the time taken for program itself to run. `sys` shows the time used by kernel. The sum of `user` time and `sys` time gives the actual CPU time.
