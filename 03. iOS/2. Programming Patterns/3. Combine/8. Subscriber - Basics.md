#### Basics of `Subscriber` protocol

Most of the times elements published by a `Publisher` are observed through closures using standard functions such as `assign{}`, and `sink{}`. Its possible however to also have custom entities as subscribers by getting them to conform to `Subscriber` protocol. Such custom subscribers are usually reference types such as a `class`.

The `Subscriber` protocol has two associated types - `Output` and `Failure`.

And these are the functions.

`receive(Self.Input) -> Subscribers.Demand` - Called when the publisher publishes an element. Inside this function a `request()` should be called on the `Subscription` argument. If `none` is specified there, no events are received.

`receive() -> Subscribers.Demand` - Available when input type is `Void`. Called when the publisher publishes a 'void' and wants to know from subscriber how many more publications does the subscriber wants it to make.

> How many values a subscriber can receive is controlled by both what is requested in `receive(subscription:)` as well as what is returned by `receive(_ input:)`. <br> The number of values to be received is additive in nature, i.e. if n values have been requested then the count cannot be reduced after that. Hence, if `unlimited` is specified then unlimited values are received. In the same vein, what is returned in `receive(_ input:)` too is additive in nature. Usually the safest thing to do is to return `.none` there as what it implies is that `receive(_ input:)` is not requesting any further increments to how many values it can receive and whatever has been specified in `receive(subscription:)` is what will happen. However, when things are dynamic enough then this can be tweaked. For example, specify `.max(1)` in `receive(subscription:)` and then manage the count on the fly in `receive(_ input:)`.

`receive(subscription: Subscription)` - Called when the subscriber has successfully subscribed to the publisher and may request more items.

`receive(completion: Subscribers.Completion<Self.Failure>)` - Called when the publisher has completed publishing, either normally or with an error.

#### Code snippet (a sample Subscriber)

> It is important to hold on to a reference to Subscription so that its not released too early (without the Subscription being in memory, events are not received).

```
/*
 It is important to hold on to a reference to Subscription so that its not released too early (without the Subscription being in memory, events are not received).
 */
class TestNotificationSubscriber: Subscriber {
    typealias Input = Notification
    typealias Failure = Never

    var subscription: Subscription?

    /* Its important that a `request()` is called on the Subscription argument. If none is specified there, no events are received.
     How many values a subscriber can receive is controlled by both what is requested in `receive(subscription:)` as well as what is returned by `receive(_ input:)`. The number of values to be received is additive in nature, i.e. if n values have been requested then the count cannot be reduced after that. Hence, if `unlimited` is specified then unlimited values are received. In the same vein, what is returned in `receive(_ input:)` too is additive in nature. Usually the safest thing to do is to return `.none` there as what it implies is that `receive(_ input:)` is not requesting any further increments to how many values it can receive and whatever has been specified in `receive(subscription:)` is what will happen. However, when things are dynamic enough then this can be tweaked. For example, specify `.max(1)` in `receive(subscription:)` and then manage the count on the fly in `receive(_ input:)`.

     `Subscription` protocol itself conforms to `Cancellable` protocol. And hence, a `cancel()` can be called on any Subscription whenever the subscription needs to be cancelled.
      */
    func receive(subscription: Subscription) {
        print("\(Date().toString()) - Received subscription")
        self.subscription = subscription
        subscription.request(.max(5))
    }

    func receive(_ input: Notification) -> Subscribers.Demand {
        print("\(Date().toString()) - Received input: \(input.name) - \(input.userInfo?["time"] ?? "")")
        return .none
    }

    func receive(completion: Subscribers.Completion<Never>) {
        print("\(Date().toString()) - Received completion")
    }
}
```

A custom subscriber created this way can then be used with some of the Publisher functions.

```
publisher1?.subscribe(subscriber1!)
```

#### Built-in Subscribers

`AnySubscriber` is a way to have a Subscriber without having to create a new entity from scratch. Its a built-in struct, and just the required Subscriber functions can be provided to it as closures.

```
let receiveSubscription: (Subscription) -> Void  = { [weak self] subscription in
   self?.cancellable4_AnySubscriber = subscription
   subscription.request(.max(5))
}

let receiveValue: (Notification) -> Subscribers.Demand = { notification in
   print("\(Date().toString()) - Received input in AnySubscriber: \(notification.name) - \(notification.userInfo?["time"] ?? "")")
   return .none
}

let receiveCompletion: (Subscribers.Completion<Never>) -> Void = { completion in
   print("Received completion event \(completion)")
}
let testAnySubscriber = AnySubscriber<Notification, Never>(receiveSubscription: receiveSubscription,
                                                          receiveValue: receiveValue,
                                                          receiveCompletion: receiveCompletion)
self.subscriber2 = testAnySubscriber
```

It can in fact even be used to wrap a custom Subscriber such that the custom Subscriber's type gets hidden (erased) from consumers.
```
publisher1?.subscribe(AnySubscriber(subscriber1!))
```

`Subscribers.Sink` is a built-in Subscriber struct that can receive an unlimited number of values.

```
let receiveInfiniteValues: (Notification) -> Void = { notification in
    print("\(Date().toString()) - Received input in SinkSubscriber: \(notification.name) - \(notification.userInfo?["time"] ?? "")")
}

let sinkSubscriber = Subscribers.Sink(receiveCompletion: receiveCompletion,
                                      receiveValue: receiveInfiniteValues)
publisher1?.subscribe(sinkSubscriber)
```

`Subscrobers.Assign` is a simple subscriber that assigns received elements to a property indicated by a key path.

#### Subscribers namespace

`Subscribers` is the [namespace](https://developer.apple.com/documentation/combine/subscribers) in which several subscriber releated types are contained. These include `Demand` struct, `Completion` enum, `Sink` class, `Assign` class.

#### Misc.

When working with custom subscribers care must be taken to consume elements at the pace at which they are published. When a publisher has high or unlimited demand, it could send elements faster than a subscriber can process them. This scenario could lead to elements being dropped, or rapidly increasing memory pressure as elements fill a buffer while they await processing. The publisher should never be blocked (but how could it be blocked?). Specify demands that you know your subscriber can keep up with.

> This concept of controlling flow by signaling a subscriber’s readiness to receive elements is called back pressure. There are back pressure operators that can be used for managing unlimited demand. Such operators include `buffer(size:prefetch:whenFull:)`, `debounce(for:scheduler:options:)`, etc. ([Link](https://developer.apple.com/documentation/combine/processing-published-elements-with-subscribers))
