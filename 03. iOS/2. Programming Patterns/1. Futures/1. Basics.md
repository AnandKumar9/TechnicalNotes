#### Futures

`Futures` are a promise of something in future, either a value or an error. And then when this value becomes available they can be used to promise another value in future (this is done using `flatMap` on the first future).

Also its possible to immediately transform a future's value (when it becomes available) to another value (this is typically done using `map` on the future).

Probably the real benefit of using them is that they make the code more readable as completion handlers do not have to be nested. They give the feel of code being synchronous and not asynchronous (which again helps in readability).

There are several iOS libraries for implementing futures - `BrightFutures`, `PromiseKit`, `FutureKit`, etc.

###### BrightFutures
A code snippet in BrightFutures -

```
User.logIn(username, password).flatMap { user in
    Posts.fetchPosts(user)
}.onSuccess { posts in
    // do something with the user's posts
}.onFailure { error in
    // either logging in or fetching posts failed
}
```

So `User.logIn` returns a `Future<User>`. A `flatMap` is used on this `Future` to return another future, `Future<Posts>`. Hence, `User.login()` as well as `Posts.fetchPosts()` need to be internally implemented in such a way that they return `Future`s.


Some common methods in BrightFutures -

`flatMap` - Applies the passed transform to return a new Future. <br>
`map` - Applies the passed transform to modify the value of Future. <br>
`zip` - Takes two (unrelated?) futures and once their values are successfully obtained, executes a closure with those values as arguments to that closure. <br>
`sequence` - Once all the futures stored in an array have succeeded, evaluates a closure (with the result of all those futures being the argument to that closure as an array). <br>
`fold` - Works on a bunch of futures and reduces them to a single value. I think a lot like array `reduce`. <br>

[Github page](https://github.com/Thomvis/BrightFutures), [documentation](http://cocoadocs.org/docsets/BrightFutures/1.0.0-beta.6/index.html)


###### Creating a Futures library/API

A primitive implementation is documented in Swift talk's episode 36. Here is my understanding of its various parts.

Create a Future, I am passing you a completion handler. I know that you will evaluate it immediately and in doing so my URL task (which is the asynchronous task here) will start right away. While invoking this completion handler you will also pass it another completion handler. I will myself call that completion handler with the data obtained from my URL task once it is over.

```
return Future(compute: { completion in
    session.dataTask(with: resource.url, completionHandler: { data, _, _ in
        guard let data = data else {
            completion(.error("No data"))
            return
        }
        completion(Result(resource.parse(data), or: "Couldn't parse data"))
    }).resume()
})
```

Yes, the Future has an initializer that takes a completion handler which takes yet another completion handler. This inner handler is eventually supposed to vend me the Result I am interested in. The initializer will immediately invoke the outer handler with an innerHandler 'send', that basically invokes  all the pending callbacks with the Result. It is the responsibility of the outer handler to invoke the inner handler when appropriate.

```
init(compute: ((@escaping (Result<A>) -> ())) -> ()) {   
    compute(self.send)
}

private func send(_ value: Result<A>) {
    assert(cached == nil)
    cached = value
    for callback in callbacks {
        callback(value)
    }
    callbacks = []
}
```

A method in Future type. This will basically append the passed callback into its list of callbacks to be called. So once the Result is known, all these callbacks actually get called.

```
func onResult(callback: @escaping (Result<A>) -> ()) {
    if let value = cached {
        callback(value)
    } else {
        callbacks.append(callback)
    }
}
```

The `flatMap` method in Future. It needs to be passed a closure which takes in the same Future type and returns another Future type B. The method itself returns the FutureTypeB. So this method is used to return a Future of another type by passing a closure that basically tells how to convert A to B.

```
func flatMap<B>(transform: (@escaping (A) -> Future<B>)) -> Future<B> {
    return Future<B> { completion in
        self.onResult { result in
            switch result {
            case .success(let value):
                transform(value).onResult(callback: completion)
            case .error(let error):
                completion(.error(error))
            }
        }
    }
}
```

Keep in mind that this entire implementation is quite primitive. For one, it does not account for thread safety. In Future's send method the callbacks property is mutated without putting thread locks, etc.
