##### Basics

Breakpoints are activated/unactivated by pressing Cmd + Y or by clicking on the Breakpoint icon on the top bar of Xcode.
If breakpoints are inactive, they would't be used during execution even if they are present.

All the breakpoints in the project can be seen in the Breakpoint Navigator (Cmd + 6).
All the currently running processes during execution can be seen in the Debug Navigator (Cmd + 5).

Breakpoints can be added and removed even during debugging.

During code execution, the code arrives and pauses at breakpoints that it goes through.
You can then move to next line of execution by pressing Step Over (F6), or to the next possible breakpoint (i.e. continue execution) by pressing Continue (Cmd + Ctrl + Y).

If you press Step Into, you go into the next inner class or method where the execution is currently paused at. Similarly, pressing Step Out probably takes you to the immediate class or method which called the current method. (Not quite. Need to check. When I kept pressing Step Out, eventually the code execution got over.)

During debugging it is also possible to right click in the narrow vertical bar on left and select "Continue To Here". Doing so, straight away brings the execution to that point going through all the lines in between (it will of course pause if it comes across any breakpoints in between). This is useful if you do not want to step over several lines one by one that you're not interested in during debugging.

All the processes are shown thread-wise or queue-wise in the debug navigator. They can also be checked using the bar just above the console area.

The variables at any point can be checked by going to appropriate process in the console area and searching for the corresponding local variable. (But sometimes it is not the local variable but the usual variable name that is shown.) Probably the variables that can be looked up are properties (both public and private), not the methods. So if a class has some properties, there values can be checked. But if the class has a method which returns some data, that data cannot be checked. It probably has to be stored in another property or variable and then its value looked up.


The value of variables can also be checked using the Variables view at the Bottom left pane. By default, Xcode only shows the variables that it determines are important. However, there is a toggle at the bottom that can be used to switch it and show all variables instead.


In Xcode 5, a quick look for several kinds of variables can also be viewed by pressing the quick look button in the tool tip which comes on hovering over that variable in the editor. Following are the types for which a quick look can be done - CGSize, NSSize, UIImage, NSString, NSAttributedString, NSPoint, CGPoint, NSData, CoreLocation, UIColor, CGColor, NSColor, UIBezierPath, NSBezierPath, NSURL.

##### Printing Objects

The best way to check values for variables that cannot even be seen in the Variables are is to use the po command in the console. Works with both gdb and lldb debuggers. The auto-completion for variable names is also there.

However, po cannot be used to print primitives and structs. For printing them, p command needs to be used and the primitives' type needs to be specified. Following are some examples.

```
p (float) _varFloatValue
p (CGRect) [[self view] frame]
```

p also always prints the address of the variable (unlike po which does not print the address for NSString).


Printing scalars in lldb console without having to use box notation -

Usually to print something like a CGRect, not just a p has to be done but also the dot notation should not be used. This can be fixed by importing UIKit in the debug session. (link)

(lldb) expr @import UIKit
(lldb) p self.dealImage.intrinsicContentSize
(CGSize) $0 = (width = 400, height = 400)

There is no need to do 'p (CGSize)[self.dealImage intrinsicContentSize]' any more.


##### Editing breakpoints

A breakpoint can even be edited with a context menu to customise it even more. For example, a regular breakpoint can be configured to be ignored the first n no. of times; or to be executed only is some condition (such as some local variables value being something specific) is met; or to do something specific when the breakpoint is encountered (such a slog a message, play a sound, etc.)

Ignore - Can be used to instruct how many times the breakpoints must be ignored.

Condition - Specifies the custom condition for breakpoint and should be understandable by llvm. If the expression deals with objects it should be typecast to a boolean. For example, (BOOL)[obj.isDataFetched isEqualToString:@"Error"].

Action - Can have several kinds of actions. Debugger command can be used to automatically print objects in the debug console. It can also be used to run AppleScript scripts, run shell commands and play a sound.

##### Exception, Symbolic and Test Failure breakpoints

Both are set up using the Add button at the bottom in the Breakpoint Navigator.

An exception breakpoint causes the program to stop execution at the line that triggers an exception, rather than simply crashing with an EXEC_BAD_ACCESS or a similar exception.

A symbolic breakpoint causes the program to pause when a specific method (such as NSObject doesNotRecognizeSelector:) or function call is made. These methods can be specified using some pre-defined symbols or particular method names. For example, objc_exception_throw is the symbol to break whenever an exception is caught regardless of whether it is caught or not. - [NSObject doesNotRecognizeSelector] catches situations where a selector is invoked against the wrong object.

Symbolic Breakpoints are actually useful when you may not have direct access to the code in question. For example when you are trying to debug a third-party library for which you only have a binary, or something in the iOS frameworks.

Syntax for symbolic breakpoints is something like this -
-[CustomViewController viewDidLoad]
Or even something generic like viewDidLoad

The method for which the breakpoint is being added is specified in the symbol field and just giving the method name itself can be enough, for example application:didFinishLaunchingWithOptions: or initWithImage:faceDetection:signatureDetection:andRegion:andScan:.

Xcode 5 also has a new kind of breakpoint (known as test failure breakpoint) which breaks when a test assertion fails.

Debug Gauges in Debug Navigator -

Apart from showing the threads and queues, Xcode Debug navigator also shows gauges which can help debug the app's CPU, memory, iCloud, Energy and OpenGL ES states. Among these CPU and Memory debug gauges are common to all kinds of apps. The gauges such as CPU and memory accomplish was Instruments can.

CPU consumption at any instant indicates if there is any activity happening at that instant and it obviously has an impact on the battery power. At a breakpoint, if the CPU gauge is showing a lot of activity just think if there is anything wrong happening in the code, any unnecessary separate thread still running, etc.

Memory consumption indicates the memory being consumed by the app. So if the CPU gauge is unexpectedly high, see if any object has been left unreleased or any inappropriate objects have been allocated, etc.

These gauges (CPU and memory) should always be checked by putting the breakpoints at correct places whenever any major feature is added or edited.
