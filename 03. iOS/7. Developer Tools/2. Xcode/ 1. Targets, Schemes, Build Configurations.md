Build Configurations -

Build configurations are specified in the Project -> Info tab. By default, 'Debug' and 'Release' build configurations are available. They are used to specify different build behaviour for the same target when needed.

Build Settings -

A build setting is a variable that contains information about how a particular aspect about the build process should be performed. It has 2 parts - the settings title (or the build setting name) and the definition (a constant or a formula used to determine the value at build time). A build setting can also have a display name, which is used to display the build setting in Xcode user interface.

Every target has its own build settings which are inherited from the project but can be overridden. In some cases, there can be different values for the same build setting in different build configurations.

Custom build settings can also be created.

One way to compare the build settings of two projects is to compare their pbxproj files using FileMerge or any other tool. The pbxproj file is present inside the xcodeproj file (rather package) of the project.


Targets -

Targets specify the output or the product that you would like to build. Some examples are iOS app, framework, and unit tests.

It contains the instructions (i.e. 'build rules') for building the product from a set of files in a project to workspace and then finally performing a set of actions on those products.

A project can contain one or more targets, each of which produces one product. The instructions of building a product are containing in the build settings and build phases of they target. A target inherits the project level build settings but can be overwritten by specifying different settings at the target level.

Targets are created by duplicating an existing target and then editing it or just tapping on the + button in project file to add a new target.

The 'build phases' in Targets specify the high-level sequence of steps performed while building the product. The build phases consist of below -

1. Target Dependencies (Other internal or external targets on which the current target has dependencies)
2. Compile sources (All source files, i.e. .m files. The compiler flags for the source files can be selectively configured as needed.)
3. Linked binaries (.framework, .a)
4. Bundle resources (.png, etc.).
Xcode 5 has also got these in addition to above - Copy Headers, Run Scripts.

Be aware that, every target creates its own sandbox on compilation so you cannot straight away assume that the data that is present in one target's bundle will also be present in another target's bundle.

Schemes -

A scheme defines a collection of targets to build (in 'Executable' field in the concerned Action in Edit Schemes) for the concerned action, the configuration to use when building them and a collection of tests to execute.

There can be any no. of schemes as desired, however only one of them is active at a time. Usually, there is a scheme for every target. When a scheme is selected, a run destination is also selected.

Every scheme has specifications for Build and all the 5 standard actions (i.e. Run, Test, Profile, Analyze, Archive) so that when any of actions is performed for that scheme, it is known how the scheme will perform it.

Schemes are automatically created when a new target or project is created and also when a project or workspace is opened for the first time.



Actions -

Actions are the various things that can be done by a scheme. There are 5 standard actions -

1. Run
2. Test
3. Profile
4. Analyze
5. Archive

Even though Build is shown along with other actions in any scheme, it is not an action itself. Build is a step that is performed before any of these actions are performed.

The unit tests to be run for a scheme are set in the 'Test' action.
Test bundles (i.e. test targets) only build for Test actions. (What is a test bundle or test target?)


Using Targets to have multiple versions -

Link 1 Link 2

Duplicate an existing target, go to build settings of both the targets and add unique preprocessor macros in all the configurations to uniquely distinguish between the targets. Then in the code, check the current target by using #ifdef and put the appropriate code in the if blocks.

#ifdef LITE_VERSION
     NSLog(@"****Lite version****");
#endif

#ifdef COMPLETE_VERSION
     NSLog(@"****Complete version****");
#endif
