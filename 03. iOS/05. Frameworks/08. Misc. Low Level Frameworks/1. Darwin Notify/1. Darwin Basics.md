Simply put **Darwin** is an unpublicized but commonly used public way to post and observe notifications even across different processes (i.e. apps). Its widely used by the OS and is in fact also used by several OS frameworks that are then used by third party apps, this is one reason that third party apps using it continues to be silently accepted by Apple.

It's based on the Mach kernel, and is hence fast and lightweight

> The conventional high level API of **NotificationCenter** can only work within a single process, i.e. app.

However note that any sophisticated data cannot be passed with the notification, you can just indicate that something happened using the notification name and likely also some lightweight integars. Also, it is literally like notifications. The notification will not get observed if the observing code is not even in memory before the notification has been posted.

> FWIW, when I posted the notification from one app by bringing it to foreground it still did get observed in the second backgrounded app and the observing code their ran when I re-foregrounded that second app. This could be unrelated though, essentially the observing app has to somehow be running and not suspended.

> Will need to check though if it actually works and is ok to use even to interact between apps with different Team IDs. Its supposed to.

Essentially - register and observe with **notify_register_dispatch()**, post with **notify_post()**, unregister with **notify_cancel()**.

### Basic Code Snippet

#### Post the notification

**notify_post()** is what posts the notification, it returns a certain int (referred to as token) which simply indicates if the notification got posted or not.

> Note that here no register was done, and that's because its not really necessary if there is no state is to be set. Just a post is enough.

```swift
import notify

@IBAction func buttonATapped(_ sender: Any) {
    postDarwinNotification("com.example.myNotification")  // The string here is the notification name
}

func postDarwinNotification(_ name: String) {
    let result: UInt32 = name.withCString {
        notify_post($0)		// notify_post is what posts the notification.
    }

    if result == 0 {
        print("\(Date().description) - ✅ Darwin notification '\(name)' posted")
    } else {
        print("\(Date().description) - ❌ Failed to post notification \(name): \(result)")
    }
}
```

#### Register for the notification and Observe it

**notify_register_dispatch()** is first used to register for the notification, and while registering for it the dispatch queue on which the callback/closure will be called (whenever the notification is posted) as well as the callback/closure needs to be passed

```swift
import notify

private var token: Int32 = 0

startObserving(name: "com.example.myNotification", callback: {
    print("Darwin notification observed in extension")
})

func startObserving(name: String, callback: @escaping () -> Void) {
  let status = name.withCString {
      notify_register_dispatch($0, &token, DispatchQueue.main) { _ in
          callback()
      }
  }

  if status == 0 {
      print("Registered for Darwin notification: \(name)")
  } else {
      print("Failed to register: \(status)")
  }
}
```

### Sharing Data

There is some specific parlance here.

**token** - A subscription ID that is provided by notify_register_* when registering for notification. This token is later needed while setting and getting data. <br>**state** - The data that can be set and then fetched.

The state is sticky, .i.e. even if any notify_register is done only after notify_post with setState has already happened, the state can still be fetched after the register_check.

Its not clear an existing notification registration (from producer or consumer) is active still. Note that when an app is quit, its registration is automatically cleared. A manual call of notify_cancel clears it up too.

> The mistake I was doing was that I was doing a notify_cancel in producer even before the consumer has done a notify_register_check.

If `notify_set_state` is done after `notify_post`, `notify_get_state` still seems to work. But its safer to set state before post.

#### Set data

First register using **notify_register_check**, then set state using **notify_set_state**.

> **notify_post** is not a mandatory step if all you want to do is set a state, and then read it later. notify_post is needed only for the subsequent notify_didpatch_register to work in the consumer app.

```swift
let notificationName = "com.example.myNotification"

@IBAction func buttonATapped(_ sender: Any) {
    resgisterCheck_SetState_Post()
}

/*
 1. Register with `notify_register_check`
 2. Set state with `notify_set_state`
 3. Post with `notify_post`
 4. Cancel with `notify_cancel`
 */
func resgisterCheck_SetState_Post() {
    var notificationRegistrationID: Int32 = 0       // This thing is called token in Darwin parlance
    let notificationAssociatedData: UInt64 = 8       // This thing is called state in Darwin parlance

    let notificationRegistrationResult: UInt32 = notificationName.withCString {
        notify_register_check($0, &notificationRegistrationID)
    }

    guard notificationRegistrationResult == 0 else {
        print("\(Date().description) - Failed to register and get an ID/token")
        return
    }

    let setStateResult = notify_set_state(notificationRegistrationID, notificationAssociatedData)

    guard setStateResult == 0 else {
        print("Failed to set state)")
        return
    }

    notify_post(notificationName) // FWIW, this is not mandatory for setting, getting state
    print("\(Date().description) Darwin notification '\(notificationName)' posted with state: \(notificationAssociatedData)")

/* While notify_cancel() is recommended to be eventually done, keep in mind that if any register() from consumer has not happened, this will render the notifictaion ineffective as the state gets reset right away */
        //        notify_cancel(notificationRegistrationID)
}
```

#### Get Data

Register with **notify_register_dispatch** and observe in its callback, in the callback get state with **notify_get_state**.

```swift
let notificationName = "com.example.myNotification"

override func viewDidLoad() {
    super.viewDidLoad()
    label.text = " "

    registerDispatch_Observe_GetState_Perform { [weak self] str in
        self?.label.text = str ?? "Recieved notification"
    }
}

/*
 1. Register with `notify_register_dispatch` and observe in its callback
 2. In the callback
     a. Get state with `notify_get_state`
     b. Perform the passed closure
 3. Even otherwise, right after
     a. Get state with `notify_get_state`
     b. Perform the passed closure
 */
func registerDispatch_Observe_GetState_Perform(perform: @escaping (String?) -> Void) {
    var notificationRegistrationID: Int32 = 0

    let notificationRegistrationResult = notificationName.withCString {
        notify_register_dispatch($0, &notificationRegistrationID, DispatchQueue.main) { _ in
            var notificationAssociatedData: UInt64 = 0
            let getNotificationAssociatedDataResult: UInt32 = notify_get_state(notificationRegistrationID, &notificationAssociatedData)

            guard notificationAssociatedData != 0 else { return }   // 0 is returned if no state was set, though FWIW state could have been set to 0

            print("Get notification data result - \(getNotificationAssociatedDataResult), Data - \(notificationAssociatedData))")
            perform("From observer - \(String(notificationAssociatedData))")
        }
    }

    guard notificationRegistrationResult == 0 else {
        print("Failed to register using notify_register_dispatch: \(notificationRegistrationResult)")
        return
    }
    print("Registered for Darwin notification using notify_register_dispatch: \(notificationName)")
}
```

### API nuances

#### notify_register_check vs notify_register_dispatch

`notify_register_dispatch` allows the passed closure to be invoked on the passed GCD queue whenever a new notification is posted, `notify_register_check` whereas doesn't give any such mechanism and is instead simply a way to get a token which can then be used to query the associated state right away.

#### notify_check

`notify_check` can be used to check if new notification has been posted since the last time it was checked using `notify_register_check`. Its useful when not using `notify_register_dispatch`.

#### notify_cancel

`notify_cancel` cancels notification and free resources associated with a notification token. 

> If notify_cancel is done before notify_post but after notify_set_state, notify_get_state still worked
