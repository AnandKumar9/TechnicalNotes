A constraint can be added in 3 different ways - Through interface builder, Programatically using the visual format language, Programmatically using the base API. Doing it through interface builder is always the easiest. It is only in some cases that the constraints are better added programatically.

An attribute can be any one of left, right, top, bottom, leading, trailing, width, height, centerX, centerY, baseline. The attributes left and right are same as leading and trailing for left to right languages and then same as right and left for right to left languages.
Usually leading and trailing should be used instead of left and right as then localization can be taken care of.

The same constraints work across different localizations. Even the leading and trailing constraints automatically flip in case of right to left localizations.

Adding Constraints programmatically -

A constraint can be created using the following class methods that uses the base API.
```
NSLayoutConstraint *cn1 = [NSLayoutConstraint constraintWithItem:button
                                                       attribute:NSLayoutAttributeCenterX
                                                       relatedBy:NSLayoutRelationEqual
                                                          toItem:self.view
                                                       attribute:NSLayoutAttributeCenterX
                                                      multiplier:1.0
                                                        constant:0];
```
In the above snippet a constraint is added from a button to its superview self.view, the button is specified first and the superview is specified next.

Here, everything apart from the constraint’s priority is specified. For setting priority, the priority property can be directly accessed.

The constraint is added to the nearest common ancestor.
[self.view addConstraint:cn1];

Also, when done programmatically it did not work if constraints are being added for a button which is being referenced using an outlet. It works if the button itself is created programmatically too.

translatesAutoresizingMaskIntoConstraints is a UIView property that indicates if the auto resizing options of a view should be automatically translated to system generated constraints. It is YES by default. Hence if automatic constraints are not to be generated, it should be set as NO. If constraints are added from interface builder, the interface builder automatically sets this property as NO.

Once a constraint is created, it can be added to a view using -addConstraint: method. Similarly, there are addConstraints:, removeConstraint:, removeConstraints: methods.

It is also possible to define constraints using visual format language using the method -constraintsWithVisualFormat:options:metrics:views:. In visual format language, - means system defined space and size is mentioned in (). Priority is mentioned with @ sign. The strings representing various views is defined in a dictionary passed in the views argument. If string names will be same as variable names for the views, a system defined macro called NSDictionaryOfVariableBindings can be used.

(Link for visual format language).

intrinsicContentSize is a UIView property that returns the natural size of the view and it sometimes needs to be invalidated to draw fresh layouts. It can be thought of as a means to tell the layout system the size that should be used as the layout system will not figure it out on its own. This usually happens with buttons as their text length can vary greatly.

needsUpdateConstraints: is another UIView property which indicates if the constraints of the view need to be updated. The system uses the value of this property to determine if it should call updateConstraints method on the view.

setNeedsLayout is a UIView method that invalidates the current layout and triggers a layout update during the next update cycle.

contentHuggingPriorityForAxis is a UIView method that returns the priority with which a view resists being made larger than its intrinsic size.
contentHuggingPriorityForAxis is a UIView method that returns the priority with which a view resists being made smaller than its intrinsic size.

In general -

To avoid ambiguity usually every view requires 4 properties or constraints specified that can let its origin and size be deduced. It need not always be the same 4 properties, but in all it is usually 4 (two in each dimension).

It not a good idea to create specific height and width constraints for a control as then the system cannot adjust the height and width as needed and the control may get rendered poorly.

Sizes are implicitly required to be at least zero and sometimes even this can lead to views not rendering as expected. So be mindful about presence of zeros as even this can cause some views to not render properly or not render at all.

Unlike struts and springs, constraints can be used for any two views irrespective of their hierarchy. However, this cannot be done if the hierarchy includes a view that sets the frames of subviews manually in a custom implementation of layoutSubviews method on UIView. It is also not possible to cross any views that have a bounds transform (such as a scroll view).
Everything that is possible through struts and springs, can be done using auto layouts too.

Typically during a display, the constraints are first applied in a bottom-top direction, i.e. the constraints of the leaf classes in a view hierarchy are applied first. Then the layout is drawn in a top-down direction and then finally the views are rendered in a top-down direction.

Debugging -

UIView has a couple of methods, hasAmbiguousLayout and exerciseAmbiguityInLayout that can be used to debug issues related to ambiguous layouts. They should not be typically needed in the final code base.
The UIView method constraintsAffectingLayoutForAxis can be used to find out the constraints impacting for the layout for the specified axis. The axis (UILayoutConstraintAxis) can either be horizontal or vertical.

In case of OS X apps, a NSUserDefaults variable called `NSConstraintBasedLayoutVisualizeMutuallyExclusiveConstraints` can be created and set as YES in `applicationDidFinishLaunchingWithOptions`. Doing so automatically calls `[NSWindow visualiseConstraints:]` whenever constraints become unsatisfiable during runtime. This method opens up a purple overlay window using which the constraints can be seen.

In debugger console, we can send `[[UIWindow keyWindow] _autolayoutTrace]` message. It shows the view hierarchy and possible ambiguous layouts.

It is good to always have identifiers for views as they are shown in the debug console during debugging as a part of the unsatisfiability log.
