### Operations

An abstract base class that represents a task.
`InvocationOperation` and `BlockOperation` are its two concrete subclasses that can be used. Or as is more commonly done, a custom subclass can be created.

Operations are either started automatically by adding them in an operation queue or started manually by calling their start method.

#####  Starting operations manually -

An `Operation` can be executed without using an `OperationQueue` by calling its `start` function directly. You need to be careful though because starting an operation that is not in the ready state triggers an exception.

Some things to keep in mind if executing an `Operation` this way.

###### Task executes synchronously
By default `start` causes the operation to be run synchronously and it blocks the thread from which it was called. So its fine if all the code in the operation is actually internally set to run asynchronously (in a different thread, etc.), but if it isn't then be careful.

As per documentation, when you call the `start` method of a synchronous operation directly from your code, the method executes immediately in the current thread.

###### Should update execution state
The default implementation of `start` updates the execution state of the operation and calls its `main` after necessary checks (i.e. any pending dependencies, etc.). Also if the overridden implementation does state management, it must also generate KVO notifications for `isExecuting` and `isFinished` key-paths when necessary.

###### Should not call super's start

The documentation states that if you override `start` you should not call `super.main()` from it (though its not clear if this is for concurrent operations or all operations). In fact even `super.start()` should not be called as if you have overridden `start` that typically indicates that you will handle everything yourself.

###### Do call main

When overridden, do call `main` or call any other code which does the job when appropriate. Or else the real task will never execute.

###### Put the real task in main -

The code to execute usually goes in `main`. The code for non-concurrent operations is usually put in it.
It need not be overridden for concurrent operations, but if the start itself calls main, then it can be overridden.

##### Additional things to be done for concurrent operations -
If the operation is concurrent, then in addition to `main`, `start`, `isAsynchronous`, `isExecuting`, `isFinished` must also be overridden.

Any overridden method or custom method in an Operation subclass must be written in a thread-safe manner. What it means is that if the method is accessed by multiple threads at the same time, it should not give inconsistent results. By default, all the existing methods in Operation are already thread safe.

##### Execution priority -

`Operation` has two properties regarding this.

`queuePriority` - Helps to chose the next task to execute when there are multiple tasks that ready. The values can be `.veryHigh` to `.veryLow`. If all the tasks have same queue priority, the task added first is executed. Could test all of this.

`qualityOfService` - This gives the priority with which the tasks are given access to system resources. This property does not have any bearing on the priority of task that the operation queue picks up. If operationA had a `background` qos and operationB had `userInteractive` qos and operationA was added before operationB, with their queuePriority being same operationA will be executed first.

##### Managing dependencies -

Dependencies can even be created across operations added to different queues.

```
addDependency(_ op: Operation)
removeDependency(_ op: Operation)
dependencies
```

`dependencies` gives the current dependencies. It should not be edited directly.

Adding the same dependency more than once results in undefined behavior and should not be done.
It is a programmer error to create any circular dependencies among a set of operations.

##### Cancelling an operation -

Once added to an `OperationQueue`, the `Operation` cannot be removed. The only way to dequeue it is to cancel it.

A single operation can be cancelled by calling its `cancel` method. All operations in an operation queue can be cancelled by calling the `cancelAllOperations` method.

The thing to note is that issuing a `cancel` command, puts the operation in the canceled state which prevents it from being run again. As a canceled operation is still considered to be finished, all its dependent operations still receive the notification to clear that dependency. 

While writing a custom operation, in addition to cancelling any possible ongoing tasks this method's implementation must do appropriate state management of `isExecuting`, etc. as well.
