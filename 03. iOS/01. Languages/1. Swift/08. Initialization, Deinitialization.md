Initialization can be done for classes, structs as well as enums.

It is required that all stored instance properties be set to an initial value by the time the instance is created. If a stored property has a default initial value, then that itself is enough. Otherwise the initializer method must assign it a value. In either case, the property observers are (thankfully) not fired (during the initial assignment that is).

It is of course also ok for stored properties that are optionals to not have a specific value or to not be assigned a value in an initializer method as they are initialized to nil anyway.

Another thing to note is that a constant property can be assigned a value only once in an initializer method (any initial default value notwithstanding). Further, in case of type constant properties this assignment cannot be done by a subclass.


###### Calling initializers

Its as if methods with init name (i.e. initializer) can be used in a special way where there is no need to say init while calling them. Also, initializer declarations do not need to have func keyword before them.

```
let boilingPointOfWater = Celsius(fromFahrenheit: 212.0)
init(fromFahrenheit fahrenheit: Double) {..
```

###### Custom initializers

Of course multiple custom initializers are possible for all the types, i.e. classes, structs, enums too.

```
init(name: String?) {..
init(name: String?, soldiers: Int) {..
```

###### Default initializer for classes

A default initializer (i.e. the simple initializer mentioned above) is automatically available for any class that provides default values for all its stored properties and does not provide any custom initializer itself. It sets all properties to their default values.

It is also the simplest initializer.

```
init() {..
```

###### Default member-wise initializer for structures

The default initializer for structures (i.e. River()) is made available only if every stored property has a default value specified (even an optional declaration does not suffice, it has to be a specific value). If this is not possible, then the cool thing is that a member-wise initializer is made available.

It automatically provides arguments for all the (stored?) properties.

```
let majorRiver: Bool // In struct declaration

let river1 = River(name: "Trident", majorRiver: true, house: houses[0])
// The member-wise initializer init(name:majorRiver:house:) used here.
```

If a custom initializer is written though for a value type (i.e. struct or enum), the default initializer is not available. This can be hacked though by writing the custom initializer in an extension, and then the default initializer becomes available.

###### Initializer delegation in value types

In case of value types, initializers can refer to other initializers using self.init(..) and this can actually be done only from initializers, not from other methods of the value type.

```
init(center: Point, size: Size) {
  let originX = center.x - (size.width / 2)
  let originY = center.y - (size.height / 2)
  self.init(origin: Point(x: originX, y: originY), size: size) // Another initializer being called here
}
```

###### Designated and convenience initializers

Classes can have two kinds of initializers - `designated`, `convenience`.

To put it simply a `designated` initializer is any initializer that is not marked as a convenience initializer. Every class must have one (even if its an inherited initializer). 

```
init(name: String?) {
  self.name = name
  self.soldiers = 400 // soldiers property should be assigned a value here as it does not have a default value
}
```

Convenience initializers are marked with `convenience` keyword. The exact need for them is still not clear to me but what rules it brings along is.
```
convenience init(knight: String) {
  self.init(location: "East")
  self.knights.append(knight)
}
```
1. A designated initializer must call a designated initializer from its superclass. (Why was this not needed when I had a NSObject subclass)
2. A convenience initializer must call another initializer from the same class (not superclass)
3. A convenience initializer must eventually call a designated initializer at some point (even if through another convenience initializer).

So to summarize, 
Designated initializers must always delegate up.
Convenience initializers must always delegate across.

1. A designated initializer must ensure that all of the properties introduced by its class are initialized before it delegates up to a superclass initializer.
2. A designated initializer must delegate up to a superclass initializer before assigning a value to an inherited property. (Or else the superclass initializer will later overwrite the values.)
3. A convenience initializer must delegate to another initializer before assigning a value to any property (including properties defined by the same class).
4. An initializer cannot call any instance methods, read the values of any instance properties, or refer to self as a value until after the first phase of initialization is complete.

Interesting links explaining these more - [link1](https://stackoverflow.com/questions/30896231/why-convenience-keyword-is-even-needed-in-swift/36612507#36612507), [link2](https://stackoverflow.com/questions/25126295/class-does-not-implement-its-superclasss-required-members/32108404#32108404)

###### Initializer inheritance and overriding

Swift subclasses do not inherit their superclass initializers by default.

If an initializer's declaration matches that of a superclass designated initializer, the override modifier must be specified. This is true even for the default initializer. And even if the subclass initializer is a convenience initializer. However, if the matching superclass initializer is a convenience initializer the override keyword is not needed (there is reason given for this, need to understand it better).
```
override init(name: String?) {
  super.init(name: name)
}
```

1. If the subclass doesn’t define any designated initializers, it automatically inherits all of its superclass designated initializers.
2. If the subclass provides an implementation of all the designated initializers in superclass (either by not providing explicitly for any and thereby inheriting or by explicitly providing for all), then it inherits all the superclass convenience initializers too.

These rules apply even if the subclass adds its own convenience initializers.
(So it seems in a simple case where a subclass does not add any designated initializer of its own, it automatically inherits all the superclass designated and custom initializers.)

Further, a subclass can implement a superclass designated initializer as a subclass convenience initializer and still not violate rule 2.

###### Failable Initializers

It allows to say that the initialization has failed and it always creates an optional. This way if the initialization needs to fail, it can report that as nil. 

If the initialization has to fail, a return nil is done. If not there is no need to actually return anything, just initializing the stored properties, etc. is enough.

```
init?(location: String?, knight: String) {
  if location == "Beyond The Wall" {
     return nil
  }
  super.init()
  self.location = location
  self.knights.append(knight)
}
```

However there can't be two initializers with the same declaration where one is failable and the other is not. The initializer declaration still needs to unique.

Example of failable initializer for enums with raw values.

```
init?(symbol: Character) {
  switch symbol {
  case "🕷", "🐋":
       self = .Kraken
  default:
       return nil
  }
}

houseKraken.sigil = HouseSigil.init(symbol: "🐋")
```

Actually all enums with raw value automatically get a failable initializer called `init?(rawValue:)`. It takes a parameter called rawValue  and selects a matching enumeration case if any.

```
houseGreyjoy.sigil = HouseSigil(rawValue: "🕷")
```

Example of initializer for enums with associated values. (May be this is how it is roughly done.)
```
init(symbol: Character) {
  var member: HouseMember?
  if symbol == "L" {
       member = .Lord(name: "Great King")
  }..
  self = member!
}
```

Failable initializer can call other initializers (from same class or super, failable or not) without any added rules. The same rules as usual initializers (i.e. designated, convenience, etc.) apply. The only thing is that if any delegate initializer fails, the error is propagated and the entire initialization is reported as failed immediately. It cannot be caught and modified in any way.

Overriding of failable initializer in a superclass to a non-failable initializer in subclass is possible.

Overriding of a non-failable initializer in a superclass as a failable initializer in a subclass is however not allowed.

And finally, the failable initializers can also be be define as an implicitly unwrapped optional in which case there is no need to unwrap the instance when created. If the creation fails though, an unwrap cannot be done and it should be checked. So this really has limited use.

```
init!(symbol: Character) {
  switch symbol {..
```

###### required initializers

Marking an initializer as required indicates that any subclass must override that initializer. And even the overriding definition should use the required modifier.
```
required init() {
```
It is not necessary though to provide an explicit implementation in the subclass, it can as well just invoke the super's initializer.

###### Deinitializers

Simple things. Used for cleanup. Only there for classes, automatically called just before instance deallocation is about to happen, cannot be explicitly called. Superclass deinitializer is called automatically at the end of a subclass deinitializer.
```
deinit { 
   NSNotificationCenter.defaultCenter().removeObserver(self)
}
```

So actually a very handy thing for non UIViewController subclasses which of course do not have methods such as viewWillDisappear, etc.

###### Misc.

In case of inheriting classes, values should be assigned to stored properties of the super class as well before the initialization gets over.

It seems as if convenience initializers exist just for the sake of properness. Its not probably ok to have a designated initializer where some of the property values are not passed as parameters.

Subclasses can modify inherited variable properties during initialization, but can not modify inherited constant properties. Within the same class though the initializer can modify a constant property once.

A damn good trick to do some more things to a property than merely specifying a default value. Just use a closure and invoke it too while assigning it as the default value.

````
let dateFormatter = { () -> NSDateFormatter in
  let formatter = NSDateFormatter()
  formatter.dateFormat = "MM/dd/yyyy"
  return formatter
}()
```
