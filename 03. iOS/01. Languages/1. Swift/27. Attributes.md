#### What are attributes

There are two kinds of attributes - `Declaration attributes` and `Type attributes`. The former are prefixed to declarations, such as struct declaration, function declaration, etc. The latter are prefix to function argument types, function types (what does that exactly mena, need to try). Most attributes are declaration attributes.

[Reference](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/attributes/)

#### dynamicMemberLookUp

Pretty similar to `@dynamicCallable` explained in this note, but works with properties. Conforming types have to implement a subscript method.

```swift
@dynamicMemberLookup
class Country {
  subscript(dynamicMember member: String) -> String {
    let properties = ["name": "Bolivia", "location": "South America"]
    return properties[member, default: "NOT FOUND"]
  }
}
```

And then at the call-site

```swift
let country = Country()
print(country.name)
```

Using this attribute allows the boilerplate `get(member:)` calls to be removed when working with Python, etc. libraries.

> The basic idea with both dynamicMemberLookup and dynamicCallable seem to be to make it seem as if a Swift file has some Python, etc.-looking type code too.

#### dynamicCallable

If a type conforms to this then it can (with a slightly different syntax at callsite, ala `callAsFunction()` ) handle invocations of arbitrary methods signatures. ([Andy Ibanez article](https://www.andyibanez.com/posts/understanding-dynamicmemberlookup-dynamiccallable-swift/))

Sample code snippet (*copied from Andy Ibanez article*) -

```swift
@dynamicCallable
class CaseChanger {
  enum Case: String, RawRepresentable {
    case uppercase = "uppercase"
    case lowercase = "lowercase"
  }
  
  func dynamicallyCall(withKeywordArguments args: KeyValuePairs<String, String>) -> String? {
    guard let casingPair = args.first, let stringPair = args.last else {
      return nil
    }
    
    guard casingPair.key == "casing" && stringPair.key == "string" else {
      return nil
    }
    
    let casingType = Case(rawValue: casingPair.value.lowercased()) ?? Case.lowercase
    return casingType == .uppercase ? stringPair.value.uppercased() : stringPair.value.lowercased()
  }
}
```

On any instance of this type, arbitrary functions can then be called. Notice though that how the function invocation on the `caseChanger` instance is different. Its like initializer invocations and has no dot after the instance name.

```swift
let caseChanger = CaseChanger()
let changedCase = caseChanger(casing: "lowercase", string: "IT WAS MANY AND MANY A YEAR AGO")
print(changedCase)
```

##### What's needed

When you mark your classes with `dynamicCallable`, you need at least one of the following methods. In the first method the arguments have to conform to `ExpressibleByArrayLiteral` protocol and in the second to `ExpressibleByDictionaryLiteral` protocol.

```swift
func dynamicallyCall(withArguments args: [AnyObject]) -> AnyObject

func dynamicallyCall(withKeywordArguments args: KeyValuePairs<String, AnyObject>) -> AnyObject
```

The first function gets invoked when a call is made to an instance without any argument names, like this.

```swift
let changedCase = caseChanger("uppercase", "Katarina Claes")
```

And, the second function gets invoked when a call is made to an instance withany argument names, like this.

```swift
let changedCase = caseChanger(casing: "lowercase", string: "IT WAS MANY AND MANY A YEAR AGO")
```

If the corresponding `dynamicallyCall()` function is not implemented but a call made still, `nil` is returned.

Note that it is also a compiler errir ar callsite when the function is called with keyword arguments or too many arguments if a tpe implements both `@dynamicallyCallable` attribute and the `callAsFunction()` function.

##### How does it help

So it all boils down to easier interoperability with other languages when writing Swift. At various points Swift has made frameworks available that allow to use libraries in other languages such as JavaScript, Python, etc. and the way to call the functions in those libraries has been with functions such as `call(with:)` . The motivation part in the proposal for this says that is a syntactic sugar that allows the boilerplate `call(with:)` to be removed from all the callsites and make them look more like the langauge they intend to be leveraging.
