##### Lazy stored properties 

A `lazy` stored property is a property whose initial value is not calculated until the first time it is used. It also must be declared as a var.

```
lazy var isMischievousHouse: Bool? = nil
```

`lazy` properties are helpful when a property depends upon outside factors that may not be available or if the property is non-trivial to create and may not even be always needed.

However, if a `lazy` property is accessed by multiple threads simultaneously and the property has not yet been initialized, there is no guarantee that the property will be initialized only once.

Also, consider this. What is happening here is that whenever dateFormatter gets accessed for the first time, the closure fires and dateFormatter gets a value. As it is a var, another value can later be assigned to it. However this closure itself does not get fired again, after all the '=' implies just the initial value.
```
lazy var dateFormatter = { () -> DateFormatter in
    let formatter = DateFormatter()
    formatter.dateFormat = "MM/dd/yyyy"
    return formatter
}()
```

###### A struct too can have lazy properties
However, such a struct instance must be declared as `var` if that `lazy` property needs to be accessed through the instance or else there is a compiler error that says _Cannot use mutating getter on immutable value_. ([link](https://oleb.net/blog/2015/12/lazy-properties-in-structs-swift/))

Also, if the lazy var is being accessed from another property that property should have a `mutable get` ([link](https://stackoverflow.com/questions/44164578/lazy-var-in-struct/44164693#44164693))

##### Computed properties

`Computed properties` actually do not store any value themselves. They instead provide a getter and an optional setter to retrieve and set other values. <br>
Also, they must be declared as `var`.

```
var isTroubleMakerHouse: Bool {
  get {
     ...
     return flag
  }
  set(newTroubleMakerStatus) {
       isMischievousHouse = newTroubleMakerStatus  // isMischievousHouse is actually another property
  }
}
```

In fact it is even possible to not specify a name in the setter (`newTroubleMakerStatus` above). In such cases, a default name of `newValue` is anyway made available. This is also termed as `shorthand setter declaration`.

A computed property with a getter but no setter is effectively a `read-only computed property`. The getter of such a property can be simplified by removing the `get` keyword and the braces. So it can be just this much.
```
var isTroubleMakerHouse: Bool {
     return isMischievousHouse
}
```

Structs and even enums(?) can have computed properties.

##### Property observers

If implemented they are called every time a property’s value is set, even if the new value is the same as the property’s current value. They can be implemented for all stored properties (even the inherited ones) that are not marked as lazy.

Property observers are not really needed for computed properties as the same thing can be achieved in their setters.

The two observers are `willSet` and `didSet`. The new and old values are made available by the compiler in `willSet` and `didSet` observers respectively.

```
var soldiers: Int = 500 {
  willSet(newCount) {
       print("New value about to be set for \(name!)s - \(newCount) from \(soldiers)")
  }
  didSet(oldCount) {
       print("New value set for \(name!)s - \(soldiers) from \(oldCount)")
  }
}
```

Again the arguments in both `willSet` and `didSet` can be omitted and just the `newValue` and `oldValue` constants be used instead which are made available by the compiler.
```
didSet {
  print("New value set for \(name!)s - \(soldiers) from \(oldValue)")
}
```

In case a property with observers is passed as an inout `argument` to a function, the observes are always called. Even if the parameter is not actually modified in the function. (Try it out? See what happens, also when the parameter is actually being changed in the function. How often are the observes called?)

Further the observes are not fired if the property value is being changed again within the observer itself.

##### Type properties

Type properties belong to the type itself, not to any one instance of that type. There will only ever be one copy of these properties, no matter how many instances of that type are created. They are usually meant for defining values that are universal to all instances of a particular type.

```
class House: NSObject {
  static let continent = "Westeros"  // It can also be a var.

print("Continent is \(House.continent).")  
// This (i.e. TypeName.staticPropertyName) is how it is always accessed or even set from anywhere.
```

They are otherwise a lot like instance properties. They too can be stored or computed properties, have a default value. However in case of stored properties, unlike the instance properties they must always be given a default value.

Internally stored type properties are lazily initialized on their first access. They are guaranteed to be initialized only once, even when accessed by multiple threads simultaneously, and they do not need to be marked with the `lazy` modifier.

##### Type methods

Type methods belong to the type (i.e. class, structure or enum) itself instead of the instance. They too have a syntax similar to type properties.

```
static func publishHouseContinent() {
  print("Westeros continent")
}
```

And as is obvious, within a type method `self` points to the Type itself rather than any instance.

Classes may also use the `class` keyword to allow subclasses to override the superclass’s implementation of that method.

##### Subscripts

`Subscripts` are basically just an alternate shorthand notation for methods in classes, structures and enums. 

The general syntax is as below. There can be any number of parameters specified and they can even be variadic parameters. However `inout` parameters and default parameter values are not allowed.
```
subscript(index: Int) -> Int {
  get {..
  }
  set(newValue) {..
  }
}
```

The type of `newValue` is inferred to be the same as that of the return value. It is not mandatory to specify the `newValue` argument in the syntax and a default `newValue` keyword is anyway made available by the complier in the setter.

Also in case of read-only subscripts, the `get` keyword can be omitted.
```
subscript(index: Int) -> Int {..
}
```

One very common usage of subscript can be to enable box notation for properties of a class, structure or enum. This allows them to have a dictionary like valueForKey behavior where a variable key string can be passed at runtime. (The below assumes that the class is a NSObject subclass and that's how value(forKey:) method is actually being used in the implementation.
```
subscript(key: String) -> String {
  get {
       guard let value = self.value(forKey: key) as? String else {
            return ""
       }
       return value
  }
  set {
       if let _ = self.value(forKey: key) as? String {
	    self.setValue(newValue, forKey: key)
       }
  }
}
```

Just like methods, subscripts too can have default arguments.


A class or structure can provide multiple subscript implementations. This is called `subscript overloading`.
