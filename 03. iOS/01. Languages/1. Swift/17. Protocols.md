Apart from delegation, protocols of course allow to specify abstract interfaces.

A protocol can be adopted by class, structure or enum. It can even be extended to actually provide some implementations too.

#### Property, Method, Initializer requirements in protocols

Must specify if the property is gettable or both gettable and settable. <br>
Type properties and methods must have `static` prefix.

In case of methods, variadic parameters are allowed but default values are not allowed. <br>

Further in case protocol is intended for structures and enums too, and if the method modifies them the method requirement should have `mutating` prefix.

Similarly initializer requirements can also be written in the protocol. While providing their implementation, they can be implemented as either `designated` or `convenience` initializer. Also, in the implementation they must have `required` keyword as prefix (unless the class is marked as `final` and hence cannot be inherited).

#### Protocols as full-fledged types (Existential Type)

```
let generator: RandomNumberGenerator    // Here generator is of a data type that conforms to RandomNumberGenerator protocol.
let things: [TextRepresentable] = [game, d12, simonTheHamster]   // Here things is an array of items that conform to the TextRepresentable protocol.
```

The `is`, `as?` and `as!` operators can also be used for checking protocol conformance.

Using a protocol as a type is also known an `Existential Type`, which comes from the phrase 'there exists a type T such that T conforms to the protocol'.

#### Two rather special kind of protocols

`Protocols with associated types` and `protocols with Self requirement` - Protocols that refer to `Self`, i.e. the conforming type or the `associatedtype` in any of its requirements aka functions (or even properties too?).

An example of a protocol with Self requirement. Notice how this Self has 's' with an upper case.
```
protocol Equatable {
	static func ==(lhs: Self, rhs:  Self) -> Bool
}
```

A protocol with Self or associatedtype requirement can't be directly declared as a type (in property, variable, function return type, etc.). It can however be made an opaque type (i.e. wrapped in `some`) and then used as a full fledged type.

#### Protocol can inherit other protocols

A protocol can even inherit one or more protocols (unlike classes for which only single inheritance is allowed). In case of function argument, `&` is used.

```
protocol Protocol1 { ..
protocol Protocol2 { ..

struct Person: Named, Aged { ..
func wishHappyBirthday(to celebrator: Named & Aged) { .. // What this means is that the celebrator parameter should be of a type that conforms to both Protocol1 and Protocol2 protocols.
```

#### Restricting conformance to classes

A protocol can be limited to be adopted only by classes by adding the `class` keyword as shown below. <br>
`protocol SomeClassOnlyProtocol: class, SomeInheritedProtocol`

#### Marking requirements as optional

Some of the requirements in the protocol can be marked as optional by using `@objc` and `optional` keywords together.

```
@objc protocol CounterDataSource {
    @objc optional func increment(forCount count: Int) -> Int
    @objc optional var fixedIncrement: Int { get }
}
```

#### Protcol Compositions

Protocl compositions allows to specify that a certain type needs to conform to multiple protocols at once. They behave as a temporary local protocol has been defined that combines requirements of all protocols in the composition. It can also be made to include one class type.

```
protocol Protocol1
protocol Protocol2 { .. }

var a1: UIView & Protocol1 & Protocol2  // Specifying UIView? however gives an error

func func1(_ : Protocol1 & Protocol2) {
```

#### Generic types with protocol are more efficient than protocol types

Internally, protocol types are wrapped in a box which is often referred to as `existential container`. For class only protocols there is a special container called `class existential container`.

It is generally more efficient to use a generic parameter than a parameter with a protocol type.

That is, here `func1` works more efficiently than `func2`.
```
func func1<A: Protocol1>(array: [A])
func func2(array: [Protocol1])
```

#### class/AnyObject inheritance

Sometimes there can be a `EXC_BAD_ACCESS` crash in protocol implementations that access `self`. And at this point its really not clear on what is an easy understandable pattern to when it happens. The fix however is to make the protocol inherit from `class` or `AnyObject`.

```
protocol UIViewControllerProtocol: class where Self: UIViewController {
```

#### Composing classes and protocols

(This was suggested in [SE-0156 Class and Subtype existentials](https://github.com/apple/swift-evolution/blob/master/proposals/0156-subclass-existentials.md) and implented in Swift 4.0.)

Its possible to declare a type to be of a specific concrete type and also be conforming to protocols at the same time.
```
let header: UIView & Protocol1 & Protocol2
```

#### Synthesized conformance in extensions for Equatable and Hashable

(This was proposed in [SE-0185 Synthesizing Equatable and Hashable conformance
](https://github.com/apple/swift-evolution/blob/master/proposals/0185-synthesize-equatable-hashable.md) and introduced in Swift 4.1.)

Protocol conformances can be synthesized in extensions and not only on the type definition (the extension must still be in the same file as the type definition).
> So what is meant by synthesizing a protocol? Well, its the fact that sometimes the compiler can automatically provide implementations for a protocol's requirements.

```
enum Either<Left, Right> {
    case left(Left)
    case right(Right)
}

extension Either: Equatable where Left: Equatable, Right: Equatable {}
extension Either: Hashable where Left: Hashable, Right: Hashable {}
```
> 👆 Look how protocol conformance itself gets conditioned on the generic types. This is an example of conditional protocol conformance.
