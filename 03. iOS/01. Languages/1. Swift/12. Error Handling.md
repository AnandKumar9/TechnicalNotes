##### What is an error type

Anything that declares conformance to `Error` protocol is called an error type in Swift. Now, the interesting thing is that this protocol does not have any requirements (i.e. properties, methods, etc. that must be implemented). So this protocol basically allows the conforming type to be _thrown_ and _caught_.

Usually however enums are used as error types.
```
enum MakeCaptainError: Error {
    case captainFewMatches
    case playMoreMatches
    ..
}
```
##### Throwing errors

If a function can throw error, it must declare that using `throws` keyword (before its return type).
```
function createFile() throws -> String
```
`throw` generates the specified error and immediately returns from the method.
```
if consideredPlayer.name == "Rahane" {
	throw MakeCaptainError.captainFewMatches
}
```

##### Catching errors -

Any time a throwing function is called it does need to be caught (or handled) from the code snippet that called it. This catching can be done in 4 ways.
1. Propagate the error from a function to the code that calls that function (`try`)
2. Handle using do-catch statement (`do try catch` )
3. Handle error as an optional value (`try?`)
4. Assert that the error will not occur (`try!`)

###### Propagating errors using `try`

Only throwing functions can propagate errors.

So what happens is that if a throwing function (func2) is called from another throwing function (func1), then if func2 throws an error then func1 does not execute any further and propagates the error to the code that called it (i.e. called 'func1'). However the throwing function call must be prepended with `try` keyword.

```
func giveCaptaincyTo(consideredPlayer: Player) throws -> Void {        
    try changeCaptain()
}

func changeCaptain() throws -> Void {
    throw MakeCaptainError.captainFewMatches
}
```

###### Catching errors using `try catch`

In case of `do`-`catch`, the method must be called with a `try` and should be inside a `do` catch. If all possible errors are not there in separate catch, then there should be one catch in the end that catches every error that is not specified.
If no error happens, remaining statements in do are executed (though here there happens to be no other statement).

```
do {
	try team1.giveCaptaincyTo(player1)
} catch MakeCaptainError.captainFewMatches {
	print("Captain in some small tournaments.")
} catch {
	print("Undisclosed")
}
```
`catch` expressions can even have a pattern with a `where` clause.


###### Catching errors using try optional (i.e. `try?`)

When the kind of error does not even matter, then try optional can be used as it gives a concise format. If there is no error, the left hand side variable is not nil and instead has whatever the function returns (even if it returns a void). If there is an error though, the left hand variable is nil.

```
if let _ = try?team1.giveCaptaincyTo(player1) {
	.. There was no error
}
else {
	.. There was some error
}
```

As of Swift3, a `try catch` still needs a `final` catch to catch any error that might not be caught using any of the preceding catch clauses. This could be designed better where if a particular `Error` type is associated with the concerned throwing function, the exhaustiveness of the catches can be enough to obviate a final blanket catch. Such an error (which currently does not exist) is what is often referred to as `typed error`.

###### Asserting that error is not expected to occur and it need not be caught (i.e. `try!`)

If a throwing function is called, but it is expected that it will actually never have to throw an error then that throwing function need not be caught using either try or try optional (i.e. `try?`). This can be done by using `try!`. If an error does happen though, there is an uncaught runtime error then.

```
let _ = try!team1.giveCaptaincyTo(player1)
```

So it may be a good thing in development as well as then any unexpected error can be noticed more easily if it happens.

##### rethrows

`rethrows` allows the compiler to waive the requirement that a call to a throwing function must be caught using try, etc. If that function which is marked as `rethrows` takes in a closure as argument then the call to the function needs to be caught only if the passed closure itself was throwing.

Almost all sequence and collection functions in the standard library that takes a function argument are actually annotated with `rethrows`. For example `map` function is throwing only if the transformation function throws itself.

Hence the 1st map below does not need to catch error, but the second one does.

```
let arr = [2, 4, 5]
let arr1 = arr.map { $0*2 }

let arr2: [Int]? = try? arr.map ({
    if $0 == 4 {
        throw LocalError.unspecified
    }
    return $0*2
})
```

##### Can be automatically bridged to `NSError`

All types conforming to `Error` can be cast to `NSError`. Hence, if a Swift error is passed to an Objective-C method it is bridged to NSError. In case the error is an enum, then its corresponding NSError's code is the case's raw value.

```
let isUserCancelled: Bool = {
    guard (error as NSError).domain == PKPassKitErrorDomain,
        (error as NSError).code == PKAddPaymentPassError.userCancelled.rawValue
    else { return false }
    return true
}()
```

##### Misc.

When the type of error matters, that is when you need to make your function a throwing function. Else just using optional or booleans as return types is sufficient.

Assertions have their place and should indeed be used. If something should really never happen, do `assert`. For example accessing an non-existent array index will result in an assertion but accessing the first element of an array returns an optional.

Since Swift treats error handling using `throw` as simple returns, its supposed to be very fast compared to other languages for similar code that deals with exceptions.

Even Xcode's documentation mark up supports a special mark up for `throws` keyword.

Swift automatically translates ObjectiveC methods of a certain format into throwing functions.

These is an additional error protocol - `LocalizedError`. It obviously has something to do with localization.

###### RecoverableError -

These is another error protocol - `RecoverableError`. Now the thing with `RecoverableError` is that it seemingly automatically allows some code to run (i.e. recovery to happen) depending on what error happens. However even though it is available in both UIKit and AppKit (i.e. macOS) it probably works only in AppKit.

Haven't tested in a macOS app, but the code is something like [this](https://stackoverflow.com/questions/40352975/how-to-use-recoverableerror-to-retry/41157102#41157102).

```
enum LocalError: Error, RecoverableError {
    case error1
    case error2
    
    var recoveryOptions: [String] {
        return ["Plenty"]
    }
    
    func attemptRecovery(optionIndex recoveryOptionIndex: Int) -> Bool {
        print("Attempted recovery")
        return true
    }}

do {
    throw LocalError.error1
}
catch {
    print("Caught")
}
```
