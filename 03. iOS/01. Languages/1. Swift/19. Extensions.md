##### Extensions

Extensions can be there for classes, structures, enumerations as well as protocols. They add functionality to them (this ability is known as `retroactive modeling`).

###### What all can extensions do

1. Add computed instance and computed type properties (but not stored properties).
2. Define instance and type methods.
3. Provide new convenience initializers (but not designated initializers).
4. Define subscripts.
5. Define and use new nested types (what is this?).
6. Make an existing type conform to a protocol.

###### Using extensions on protocols
```
extension TypeA: Protocol1, Protocol2 {
	..
}
```

Here a `TypeA` (which could be a class, struct, anything) is being extended to conform to `ProtocolA` and `ProtocolB`.

###### Providing default implementation of protocol requirements

In case of protocols, extensions can even be used to provide a default implementation for existing methods. So if the conforming type already provides an implementation that implementation is used and if it does not then the default implementation from the extension is used. <br>
This can be done for even existing system protocols (keep in mind that with extensions existing types can even be made to conform to protocols).

It is also possible to add an implementation to a protocol extension for a method that is not declared in the protocol at all, i.e. that methods is not a mandatory requirement in the protocol. In such a case too, the new method gets available to all the conforming types of that protocol anyway.

The standard library uses this technique a lot. For example, `map` method in Sequence protocol too has a default implementation for all conforming types (Array, Dictionary, etc.). And if you want you can override that implementation for specific conforming types.

###### Extending protocols using constraints

Protocols can be extended using constraints to ensure that the included implementation is available only for certain satisfying types. <br>
`extension Collection where Iterator.Element: TextRepresentable { ..`


Apparently type constraints can even be there at function level and not just extension level. Protocols with associated types or Self requirements too can be used here (even though they cannot otherwise be used as full fledged types). <br>
`func nextInt<I: IteratorProtocol>(iterator: inout I) -> Int? where I.Element == Int { .. }`


Specific generic types (and not just protocols) too can be extended using constraints. Available since 3.0. <br>
`extension Array where Element: Comparable {`


And 3.1 goes further and allows these constraints on generic types to be checking the associated types for specific concrete types. <br>
`extension Array where Element == Int {`

###### Synthesized protocol conformance`

Extensions cannot override existing functionality.

Swift 4.1 onwards compiler can automatically synthesize protocol conformance for certain types. For example, structs where each element already conforms to `Equatable` now automatically conforms to `Equatable` if just the conformance gets explicitly declared.

[SE-085 Synthesizing Equatable and Hashable conformance
](https://github.com/apple/swift-evolution/blob/master/proposals/0185-synthesize-equatable-hashable.md)

###### Static and dynamic dispatch with protocol extensions

There is a subtle difference between mandatory and optional requirements.

With mandatory protocol requirements, `dynamic dispatch` is used while selecting method implementations. Whereas with methods that are not mandatory requirements in protocol, `static dispatch` is used.

Hence in below example, even though `b` is initialized using `Struct1` but declared as a `Protocol1` conforming type, `method2` implementation of `Protocol2` is used. Whereas with `a`, `method2` implementation of `Struct1` is used.

```
protocol Protocol1 {
    func method1()
}

extension Protocol1 {    

    func method1() {
        print("extension default implementation of mandatory protocol method")
    }   

    func method2() {
        print("extension implementation of non-mandatory protocol method")
    }

}

struct Struct1: Protocol1 {
    
    func method1() {
        print("Struct1 implementation")
    }

    func method2() {
        print("Struct1 implementation")
    }
}

let abc = Struct1()
abc.method()    // This runs the method implementation in Struct1
abc.method2()   // This runs the method implementation in Protocol1 extension

let a: Struct1 = Struct1()
let b: Protocol1 = Struct1()

a.method1()    // This runs the method implementation in Struct1
b.method1()    // This runs the method implementation in Struct1

a.method2()    // This runs the method2 implementation in Struct1
b.method2()    // This runs the method2 implementation in Protocol1, even though b is initialized as Struct. And that happened because its type is declared as Protocol1.
```
