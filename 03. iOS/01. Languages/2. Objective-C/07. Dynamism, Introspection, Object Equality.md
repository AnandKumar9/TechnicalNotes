##### Dynamism

The class of an object is determined at runtime and it hence does not necessarily matter what type an object is statically typed to. The actual type is determined during runtime.

##### Introspection

Introspection is the ability of objects to divulge information about themselves during runtime. NSObject protocol includes several methods that help in introspection.

`-class` - Returns the class of self. Returned as an object of type Class. <br>
`-superclass` - Returns the class of super. Returned as an object of type Class. <br>
`-isKindOfClass:` - Returns yes if the receiver is an instance of the specified class or ultimately inherits from an object of the specified class. <br>
`-isMemberOfClass:` - Returns yes if the receiver is an instance of the specified class. <br>
`-conformsToProtocol:` - Returns yes if the receiver conforms to the specified <br> protocol. The argument is of type Protocol, i.e. @protocol(). <br>
`-respondsToSelector:` - Returns yes if the receiver implements or inherits a method that can respond to the specified message. The argument is of type SEL, i.e. @selector(). In fact, instancesRespondToSelector: method can also be used for the same thing. <br>

If a C-based function exists or not can be checked just by comparing the function name to NULL.
```
if (UIGraphicsBeginPDFPage != NULL) { .. }
```

##### Object Equality

The `isEqual:` method provided by `NSObject` just checks for pointer equality, i.e. whether the objects being compared point to the same memory address or not. This is not good enough if you do not want (and you likely would not) two objects whose attributes are all otherwise equal to be deemed as unequal.

> It can be said that `isEqual:` checks if the identity of the objects is same or not. Every distinct object is said to have a different identity, which is nothing but its memory address.

Hence, some of the classes in Foundation framework themselves provide different methods for comparing equality which instead compare the constituting values.

NSString (isEqualToString:),
NSDate (isEqualToDate:),
And similarly for NSDictionary, NSNumber, NSAttributedString, NSHashTable, NSIndexSet, NSOrderedSet, NSSet, NSTimeZone, NSValue, NSData. Note that in all these methods, nil is not a value argument and raises an exception.

Any two instances of these classes should be compared using these methods instead of `isEqual:`.

> A peculiar case with `NSString` is that even if two separate immutable strings objects are created but then given the same value, for optimisation reasons they point to the same copy. This optimisation technique is known as string interning and is actually done for selector names too.

Now if `isEqual:` has to be overridden for any of the custom classes or other Foundation classes to get rid of this mere pointer comparison, a few things have to be taken care of. <br>

a. A new `isEqualTo<Class_Name>` method must be implemented which actually performs a sensible comparison. <br>
b. Override `isEqual:` to do basic checks such as the objects being compared are of same class and then to call the isEqualTo<Class_Name> method. <br>
c. Lastly, but importantly the hash method should be appropriately overridden. <br>

`hash` is a NSObject method that basically returns an integer (which can be thought of as a table address). If two objects are equal (i.e. isEqual: is true for them), they will have the same hash value. However, if two objects have the same hash value it does not necessarily imply that they have the same memory address.

Hence when the hash method has to be overridden, it should return same unique values for equal objects. That's all.

Practically speaking, all this is mostly not needed. Objects are seldom 'equal' as some attribute or the other will be different.

The thing to remember is that if `isEqual:` is overridden, `hash:` should also be overridden, especially if these objects are going to be placed in collection classes such as NSSet, NSDictionary, etc. The collection classes refer to hash: very often.
