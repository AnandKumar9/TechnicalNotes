### OperationQueue

Manages operations. After being added to operation queue, the operation remains in the queue until it finishes executing its task or is explicitly cancelled. It is thread safe and the same `OperationQueue` instance can be used from multiple threads at the same time.

If an operation is already in one queue, the same operation instance cannot be put in another queue. Otherwise there is an exception.

##### Creating/getting an OperationQueue -

```
OperationQueue.main
OperationQueue.init
OperationQueue.current
```

###### OperationQueue.main

Returns the operation queue associated with app's main thread. Its `underlyingQueue` property obviously returns the main queue and cannot be set to anything else. This queue executes the operations only one at a time (regardless of the operation queue's `maxConcurrentOperationCount` value). The execution of operations gets interleaved with other tasks that have been submitted to the main thread.

> Could recreate that only one operation is run at a time. Whereas if the operation queue used was not `OperationQueue.main`, multiple operations were running at the same time. So this part is good.

> So it seems that a thread too can only do one thing at a time. And that's what is logical, isn't it. There isn't any magic happening anywhere.

###### OperationQueue.current

Returns the operation queue the operation is currently running in. So it must be called from the context of a running operation. Or else it returns `nil`. And if the `Operation` has been run manually by calling `start`, then probably this return `nil` (what though if the start was called from main of another `Operation` which in turn is being run through an `OperationQueue`).

##### Managing operations -

```
addOperations(_:waitUntilFinished:)
addOperation(_ op: Operation)
addOperation(_ block: @escaping () -> Void

waitUntilAllOperationsAreFinished
cancelAllOperations

isSuspended
operations
operationCount
maxConcurrentOperationCount
```

`addOperations(_:waitUntilFinished:)` - Adds the operations in the array mentioned in first argument to the operation queue. If `waitUntilFinished` is marked as true, the current thread is blocked until all the specified operations finish executing.

`addOperation(_ op: Operation)` - Adds the specified operation but does not block the current thread.

`addOperation(_ block: @escaping () -> Void)` - Adds the specified closure by wrapping it into an Operation object. So it looks like a pretty neat and handy thing. No need to subclass Operation, provide main implementation, etc. Just put the necessary code in a closure and add it to the operation queue. Once the closure is over it is probably automatically assumed to be finished. So it can easily be used for simple tasks.

`operations` - Gives the currently queued operations in queue in the order that they were added which need not be the same as the order in which they get executed. It does not include the operations that have already finished executing.

`operationCount` - Gives the no. of operations currently in queue. As operations get over, this count changes. So it just seems to be a computed property which returns operations.count.

`waitUntilAllOperationsAreFinished` - Blocks the current thread until all the operations in the receiver operation queue have finished executing. During this time, operations can still be added to the receiver operation queue from other threads.

`isSuspended` - A settable property. If set to true, the queue does not start any new operation but already executing operations continue. Also operations can still be added to the queue. Its default value is false. It can be observed using KVO.

##### Implemented as a wrapper around dispatch queues (but not always) -

Technically it is said to be a wrapper around `DispatchQueue`, but that may not always be true. It executes its operations either directly, by running them on secondary threads or indirectly using the GCD. So sometimes it probably does not use dispatch queues but instead interacts directly with threads.


`underlyingQueue` -
Is a settable property that gives the dispatch queue that the operation queue is using. <br>
Its default value is nil (what is the associated dispatch queue then? Probably nothing and that is the case when a operation queue runs its tasks directly). If I do not myself assign a dispatch queue to the underlyingQueue property, it always returns nil. Even when it is running. <br>

It can be set to an existing dispatch queue in which case the upcoming operations of the operation queue get queued behind the dispatch blocks already submitted to the dispatch queue. However this should be only done only when the operation queue does not already have any operations else an exception is raised. Also value of this property must not be set as the value returned by `dispatch_get_main_queue()`.

Keep in mind that operation queue and dispatch queue do not necessarily have a one-to-one mapping, a dispatch queue may of course have tasks from multiple operation queues in it.


##### Order of operations execution -

Operations within the queue (but not yet executing) are themselves organized according to priority levels and inter-operation object dependencies. For operations that are ready to execute, the operation queue always executes the one with the highest priority (`queuePriority`) relative to the other ready operations. If two operations are ready and have the same priority, then the one that was added first is executed first.

##### Default QoS -

`qualityOfService` - An `OperationQueue` property that indicates default QoS to apply to all the operations in the queue. So this is the QoS applied if the operation does not have a QoS of its own. (QoS propagation across dispatch queues is a more detailed topic and has more rules to it.)

##### KVO compliant properties -
Some of the `OperationQueue` properties are already KVC and KVO compliant.

