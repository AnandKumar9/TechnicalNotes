The main function -

As a part of the launch cycle, the system creates a process and a main thread for the app and calls the app’s main function on that main thread. The default main function promptly hands the control back to the UIKit framework. In the main function’s UIApplicationMain call, argc and argv contain any launch time arguments passed to the app, the 3rd argument specifies the principal app class responsible for running the app (it should usually be left as nil as then by default UIApplication is used) and the fourth argument identifies the class of custom app delegate.

return UIApplicationMain(argc, argv, nil, NSStringFromClass([MyAppDelegate class]));

App launch -

When an app is directly launched into background, the system still loads the app’s main interface files but it does not display the app’s window.

applicationState property (of the shared UIApplication object) in application:willFinishLaunchingWithOptions: or application:didFinishLaunchingWithOptions: can indicate if the app is launching into foreground or background. When being launched into foreground, its value is UIApplicationStateInactive and when being launched into background, its value is UIApplicationStateBackground.

Apps that use OpenGL ES should not use application:willFinishLaunchingWithOptions: and application:didFinishLaunchingWithOptions: methods to prepare their drawing environment. Instead the OpenGL ES drawing calls should be made in the applicationDidBecomeActive: method.

application:willFinishLaunchingWithOptions: and application:didFinishLaunchingWithOptions: methods should be kept as lightweight as possible to reduce the app’s launch time. Apps are expected to launch and initialize themselves and start handling events in less than 5 seconds. If the app does not finish its launch cycle in this time, the system removes it. Hence, any task that might slow down the launch must be executed asynchronously on a secondary thread.

If an app supports only landscape orientation, UIInterfaceOrientation key must be added in info.plist and its value must be set to UIInterfaceOrientationLandscapeLeft or UIInterfaceOrientationLandscapeRight. This key tells iOS that it should configure the orientation of the app status bar (if one is displayed) as well as the orientation of views managed by any view controllers at launch time. Using this key is equivalent to calling the setStatusBarOrientation:animated: method of UIApplication early in the execution of your applicationDidFinishLaunching: method.

Also, any app-specific data files should be created in the Library/Application Support/<bundleID>/ and the app bundle itself should never be modified.

Responding to interruptions -

In case of an alert based interruption (such as an incoming phone call) an app temporarily moves to an inactive state and stays in it until the user dismisses the alert, upon doing which the app may either come back to active state or move to background state.

In case of iOS5, banner based notifications do not move the app to inactive state. However if the user pulls down the banner to see the notification center then the app moves to inactive state.

Pressing the sleep/wake button moves the app to background state but sets the applicationState property to UIApplicationStateInactive (and not UIApplicationStateBackground).

When an app receives an interruption and is about to move to inactive or background state, applicationWillResignActive: method is where the app should prepare for moving out of active state. This may include things such as stopping timers, pausing the state in case of a game, throttling OpenGL ES frame rates, etc. Another thing which must be done in this method is to close any references to open files configured with NSFileProtectionComplete option as then the encryption for them can be enabled.

When the app moves back to active state, the applicationWillBecomeActive: method should reverse any of the steps taken in applicationWillResignActive: method.

When the user receives a call and comes back to the app during the call, the height of the status bar increases to indicate that the user is on a call. If the views are being managed through view controllers, the view controllers automatically take care of adjusting height of the managed views. If the app does not use view controllers, then it can deal with it manually by registering for UIApplicationDidChangeStatusBarFrameNotification.

When app moves to background -

When an app moves to background, it can perform the required tasks in applicationDidEnterBackground: method. In this method, the app must save all the required data and also clean up as much memory as it can. Further, if the app does not wish a screenshot of the app’s user interface at the time of entering background to be taken by the system (which it automatically does otherwise) then it must hide or modify those views before the applicationDidEnterBackground: method returns.

applicationDidEnterBackground: method gets approximately 5 seconds to finish the tasks and return and if it doesn’t the system automatically removes the app from the memory. If for any reason an app needs more time, it should call the beginBackgroundTaskWithExpirationHandler: method to request more background execution time and start any long-running task in a secondary thread. The applicationDidEnterBackground: method must still return in 5 seconds.
This method does not define a new task and starts it, it instead just tells the system to give some more time while the already started tasks are executed. (link)

UIApplicationDidEnterBackgroundNotification is posted when an app is entering background.

Returning to foreground -

When an app is about to move to foreground, applicationWillEnterForeground: method is called. The tasks that were performed in applicationDidEnterBackground: method can be reverted here. applicationDidBecomeActive: method should basically just continue to perform tasks as it would at launch time.

UIApplicationWillEnterForegroundNotification is posted when an app is entering foreground.

Notifications queued when app is in suspended state -

When an app is in a suspended state, the system keeps on queueing all the notifications (such as time change, preferences changes, external accessory connected, device orientation changed, iCloud account status change, etc.) it receives for the app in this time and delivers them when the app starts executing code again (whether in foreground or background). However, the system also coalesces the relevant notifications together to prevent an overload of notifications. These queued notifications are delivered on the app’s main run loop and are usually delivered before any touch event. (list of possible notifications)

NSUbiquityIdentityDidChangeNotification - Posted if the status of iCloud changes for any reason
NSCurrentLocaleDidChangeNotification - Posted if the user changes the device language.
NSUserDefaultsDidChangeNotification - Posted if the app’s settings in Settings app have changed.

UIDeviceOrientationDidChangeNotification - Posted if the device orientation changes. In addition, the view controllers update their interface orientation automatically.

Further an app returning to foreground also receives view-update notifications for any views that were marked dirty(?) since the last update. Also, an app running in the background can still call setNeedsDisplay and setNeedsDisplayInRect:. However, as the views are not visible these updates are made only when the app returns to foreground.

App termination -

If the app is configured with the UIApplicationExitsOnSuspend key, it never enters background or suspended modes and instead just cycles between not running, active and inactive states. When the user presses the home button, applicationWillTerminate: method is called and the app gets 5 seconds to return from it (after which the app is terminated).

If the app is running at termination time (i.e. executing code in foreground or background), the system calls applicationWillTerminate: method. This method must do the necessary tasks and return within 5 seconds. If the app is in suspended state and terminated this method is not called.

Run Loop -

An application’s main run loop is used to process events and handle updates to the view-based interfaces. Probably touch events are only done in main run loop and not in any other run loop. However some other events such as accelerometer events are not delivered using main run loop, but instead to the designated delegate object(?).

There are several types of events (touch, remote control, motion, accelerometer, redraw, location, etc.) and all of them are handled differently. Touch and remote control events are handled by responder objects. UIApplication objects, view objects, view controller objects are all examples of responder objects.
