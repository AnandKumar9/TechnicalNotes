`Fastlane` is a way to automate some of the commonly done tasks. Its scripts are written in Ruby and it is installed as a Ruby gem on the system where it is run.


###### Terminology

`fastfile` - The file in which tasks to be performed are put. <br> <br>
`lane` - The various custom functions created in a fastfile. <br> <br>
`action` - Typically means the built-in actions that Fastlane already provides. Custom actions can also be created. An action literally though is nothing but a standard task, say running the tests (the corresponding action is scan).

###### Command line commands

`fastlane init` - Initializes fastlane, i.e. creates a Fastlane folder in the project's directory and also creates an empty fastfile.<br><br>
`fastlane lane1` - Runs a particular lane of the fastfile

`bundle exec fastlane lane1` - The prescribed way to use fastlane. Its supposedly faster, but what does it exactly do. Its somethng about the fact that it makes all the gems specified in the gemfile available for the program.

###### Lane syntax

```
lane :lane_name do
  ...
end
```

Here is how arguments can be passed to a lane when that lane is called from another lane.

```
lane1(parameterA: "abc", parameterB: "irty")

lane :lane1 do |parameters|
  xyz = parameters[:parameterA]
  lmn = parameters[:parameterB]
  ...
end
```

###### before_all, before_each, etc. -

`before_all` - <br>
`after_all` - Runs only if the lanes have been run successfully. So it is apparently not run if the lane had a scan and any of the tests failed.
`before_each`
`after_each`

It seems to me that a `fastfile` can be told only to run one lane at a time. Now it may be the case that this lane in turn is calling other lanes internally. And that is where `before_each` and `after_each` matter. They get called for each of the lanes but `before_all` and `after_all` get called only once.

`before_each` and `after_each` lanes also get parameters that specify which lane has been called and with what parameters. The sequence is important, the naming of the parameters is not. It's not mandatory to specify these parameters in the lane, they can also be omitted if not needed.

```
before_each do |lane, options|
  UI.message(lane)               # Prints lane name
  if lane == :laneTest2          # If the currently called lane is laneTest2
  end
  if options[0]                  # If parameters have been passed to this lane
    if options[0].key?(:key1)    # If one of the parameters is called ley1
    end
  end
end
```
For some reason, `options` is an array and its first element has all the passed parameters as a dictionary. <br>
`[{:key1=>1, :key2=>2}]`
> Why isn't `options` a dictionary to begin with?



Even `before_all` and `after_all` get passed these things. I have not tested options, but this too must be possible (i.e. it will give any parameters that might have been passed while invoking the lane through fastfile).

```
before_all do |lane, options|
  UI.message(lane)  # Prints lane name for which fastfile has been invoked
end
```

As the `all` methods make available an argument called `lane`, it also goes with my understanding that fastlane can be asked to invoke only lane at a time.

###### Lane contexts -

There exists a shared hash (i.e. dictionary) across actions that can be used to communicate values.
So they apparently are a way for built-in actions to communicate data to other actions. This is the syntax.
`lane_context[SharedValues::VARIABLE_NAME_HERE]`

Here is an example.
```
# Generated by 'increment_build_number', but that is an action and not a lane.
lane_context[SharedValues::BUILD_NUMBER]
```

All the shared values made available by an action can be found by running `fastlane action <action name>`

###### Environment variables -

Environment variables are variables that are available across all the fastlane files (i.e. fastfile, config files, plugins, etc.). They are typically declared in a `.env` file and are accessed using `ENV['']` syntax.

```
FL_GITHUB_API_SERVER_URL=https://github.kdc.capitalone.com/api/v3/            # Declaring an env variable in .env file

ENV["SLACK_URL"]        # Accesing env variables from elsewhere in the code (such as a Fastfile)
```

It is also possible to create an env variable from fastfile itself, although this is not the usual way to do it.
```
ENV["DELIVER_USER"] = "felix@krausefx.com"
```

###### Plugins -

`Plugin` is probably just a collection of custom actions.

###### Misc. -

To actually be able to run lanes, the Xcode scheme must be marked as 'Shared'. Else it will give an error which says 'Could not find Scheme.'

For any interaction with user its better to use UI helper (`UI.message`, etc.) class rather than using puts, gets, etc.

If a lane is declared as `private_lane`, it cannot be called directly from the command line. So it should be used accordingly.

Never put a password in fastlane file, use environment variable.
