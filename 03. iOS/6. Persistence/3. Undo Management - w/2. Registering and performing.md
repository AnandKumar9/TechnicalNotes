Registering undo operations.

It can be done in 2 ways.

1. Simple undo - An undo operation is registered by passing an argument that holds the attributes of the object prior to the change. This is done using registerUndoWithTarget:selector:object: method. Here, target specifies the object to which message whould be sent when undo is done, selector the selector that should be invoked, object specifies the argument that should be passed to that selector. This argument contains the previous attributes of the object and is usually a dictionary. The specified selector should be capable of taking the passed argument and reverting the object to its previous state.

Here is a code snippet.

- (void)setMyObjectTitle:(NSString *)newTitle {
    NSString *currentTitle = [myObject title];
    if (newTitle != currentTitle) {
        [undoManager registerUndoWithTarget:self selector:@selector(setMyObjectTitle:) object:currentTitle];
        [undoManager setActionName:NSLocalizedString(@"Title Change", @“title undo")];
        [myObject setTitle:newTitle];
    }
}

While doing an undo, the registerUndoWithTarget:selector:object: method obviously gets called again but the undo manager takes care of adding it to the redo stack and not the undo stack as it is still in process of undoing.

2. Invocation based undo - An undo operation is registered using an NSInvocation object (not directly though). prepareWithInvocationTarget: is the method used, but the argument to this is not an NSInvocation object instead instead the argument is an id object which represents just the target of the undo operation. This is the object on which the undo manager calls a method when an undo is needed. The undo manager is then sent a method with the old values being passed to it, which actually belongs to the object for which undo is being implemented. This method actually does the undo. However, the undo manager obviously does not implement this method instead it has forwardInvocation: set up and hence can forward this method to the object that was previously informed to it. And thats how it all works. (forwardInvocation: uses NSInvocationOperation, NSUndoManager internally takes care of preparing the NSInvocationOperation object.)

- (void)setMyObjectWidth:(CGFloat)newWidth height:(CGFloat)newHeight{
    float currentWidth = [myObject size].width;
    float currentHeight = [myObject size].height;
    if ((newWidth != currentWidth) || (newHeight != currentHeight)) {
        [[undoManager prepareWithInvocationTarget:self] setMyObjectWidth:currentWidth height:currentHeight];
        [undoManager setActionName:NSLocalizedString(@"Size Change", @"size undo")];
        [myObject setSize:NSMakeSize(newWidth, newHeight)];
     }
}

Performing Undo and Redo.

Undo and redo are done by calling undo and redo methods.

The undo message closes the last open undo group and then applies all the operations in that group, recording them as redo operations as well alongside.

The redo message similarly applies all the redo operations in the top redo group.

It is also possible to have nested undo groups, i.e. an undo group within an undo group. To undo nested groups, the group must be explicitly closed with an endUndoGrouping message and then undoNestedGroup must be used to undo it. Also even if automatic grouping is explicitly turned off (by default it is turned on) through the setGroupsByEvent: message, the undo group must still be explicitly closed before performing an undo.


Clearing the undo stack.

removeAllActions clears the entire undo and redo stack.

However there are cases where only some operations need to be selectively cleared. An NSUndoManager object does not retain the targets of undo operations. Hence, there is always a risk of sending an undo operation to an object that might have already been deallocated. In such a .1, the client should send removeAllActionsWithTarget: (passing self as the argument) to the undo manager before releasing it in its dealloc method.

Setting action names.

While registering undo operations, names can be given to them. Undo and redo can then be done using these names with methods undoMenuTitleForUndoActionName: and redoMenuTitleForUndoActionName:. This is usually needed in Mac drawing apps where menu items can be created for undo and redo operations.

whenever an undo manager opens or closes a new undo group (except when it opens a top-level group), it posts an NSUndoManagerCheckpointNotification (it is also posted when the undo manager checks the redo stack in canRedo).  The undo manager’s client should register itself as an observer for this notification and record undo operations for all pending changes upon receiving it. There are also more notifications posted when an undo group is created, closed, an undo is actually done, etc. Opening and creating an undo group are probably different things.

A NSUndoManager property should be synthesized or else clang compiler gives a warning that another property synthesizes it as readonly (link). (It isn’t yet clear why though.)
