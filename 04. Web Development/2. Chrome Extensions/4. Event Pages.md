OK so event pages are background pages that are loaded only when needed and when they are not doing anything they are unloaded (automatically?) to free up memory and other system resources.

The fact that a background page is event page is specified by the persistent key in manifest file. And the actual js file can be named anything.

```
"background": {
    "scripts": ["eventPage.js"],
    "persistent": false
},
```

###### Lifecycle of an event page -

Things that cause an event page to load -
	1. Extension is installed or updated
	2. The page is listening for an event which then gets triggered
	3. A content script or another extension sends it a message
	4. Some UI in the extension calls runtime.getBackgroundPage.

Once started an event page does not unload until all the UI belonging to the extension has been closed and the message ports closed as well.

`runtime.suspend` event is dispatched to the event before Chrome closes the event page. It should be handled in a few seconds. If during this time though something causes the event page to be normally loaded, the suspension is cancelled and `runtime.onSuspendCanceled` triggered instead.
The entire lifecycle of an event page can be viewed using Chrome's task manager.


###### Event registration -

`addListener` should be called for the necessary events every time the event page loads. And it probably should also be called in some way at `runtime.onInstalled`. (Need to see this working.)

It seems as if the only way an extension can listen to an event is from an event page.
