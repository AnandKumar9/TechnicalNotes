#### Fast forward merging

Say branch2 is created from branch1 and two commits 2A and 2B are added in branch2. Then you come back to branch1 and just want to merge in the changes from branch2. For such simple cases where they have been no other commits done in branch1, Git by default does a fast-forward merging.

If a merge is done, by default fast-forward merge will happen and the commit history will look like this - `2A 2B`.
If however no fast forward merge is done, the commit history will look like this - `2A 2B M`.

So in case of no fast forward merge, a merge commit is specifically added.

```
git merge branch1 (Do a fast forward merge if possible)
git merge --no-ff branch1 -m "No ff" (Do a non fast forward merge)
```

Github by default only does no fast forward merges.

#### Rebasing

Say branch2 is created from branch1 and two commits 2A and 2B are added in branch2. Then you switch back to branch1 and add two more commits 1A and 1B to it. Now you switch back to branch2 and want to take the latest changes from branch1.

If a merge is done, the commit history will look like this - `2A 2B 1A 1B M`. <br>
If a rebase is done instead, the commit history will look like this - `1A 1B 2A 2B`. <br>
(`M` above denotes a merge commit that says branch1 was merged onto branch2)

So there isn't an extra merge commit and it's also as if branch2 commits started after 1B, i.e. branch2 is now based on a new commit. This is good as it gives a cleaner and sequential history for the changes that branch2 actually did.

While pulling changes from upstream, it is advised to do a rebase instead of merge.


> So if you rebase branchA onto your current feature branch, then the last commit of branchA will now show up as the base from which commits of your current feature branch have started.


###### How rebasing works
If you are rebasing branch1 (current branch) onto branch2, first the delta between branch1 and common ancestor is stored in a temp file, then branch2 is made the current branch and then the stored delta is applied on it.  <br>
And then a merge still needs to be triggered on branch2 with the branch1. The end result is same as a simple merge but this gives a cleaner commit history. Rebasing causes the commit history to appear as if there was no separate branch.


###### Commands
```
git checkout branch2
git rebase branch1 (This rebases branch2 on to branch1)
git checkout branch1 (branch1 still needs to be checked out and then merged with branch2)
git merge branch2
```

###### Interactive rebasing

With Interactive rebasing it's possible to modify every incoming commit from the new 'base' branch. It's possible to do any of these for every commit.

```
# p, pick = use commit
# r, reword = use commit, but edit the commit message
# e, edit = use commit, but stop for amending
# s, squash = use commit, but meld into previous commit
# f, fixup = like "squash", but discard this commit's log message
# x, exec = run command (the rest of the line) using shell
# d, drop = remove commit
```

`git rebase --interactive master`

On doing so, the interactive editor then shows all the incoming commits and you can decide the appropriate action for every commit and then save it. Then for any commit that needs modifying, git prompts you to give the required information (such as the new commit message).

[link](https://help.github.com/articles/using-git-rebase-on-the-command-line/)

###### Using interactive rebasing to combine old commits into one - <br>
Say there is a repo with commit history (in reverse chronological order) `C1 C2 C3 C4 C5 ..` and you want to combine `C2 and C3` into one. And also that all this is on `master`. <br>

`git rebase --interactive <C4 commit hash> master` <br>

This brings up the interactive editor. <br>
Type `i` to edit it <br>
Write `reword` for C3 commit <br>
Write `squash` for C2 commit <br>
Press `escape` to escape editor <br>
Type `:x` to save and quit <br>
In the new prompt that comes similarly enter the new commit message and save

The commit history will now be - `C1 CNew C4 C5 ..` <br>
`C1` though I think gets a new commit hash

###### Using interactive rebasing to reorder commits - <br>
Interactive rebasing editor can similarly also be used to reorder commit history. You just have to manually specify commits (by doing a cut and paste) into the desired order and save and quit (i.e. `:x`).

#### Fixup and Autosquash

Fixup allows to add a commit in such a way that its an indication to Git that if an interactive rebase is done later on, it should squash this new commit onto another specified older commit. Its handy when there is an older commit where a small change needs to be added, and you want to keep your commit hitory clean still.

So if there is a commit history such as this.
```
f31f60ff2a0 Result > hubPaymentCards
0e217d2dd70 APICallStatus > digitalCardEligibility
470cbf3517c APICallStatus > GetAuthorizationStatus
7fab88abf08 APICallStatus > CardHolders
```

And there is a need to modify something in 2nd commit (0e21), then make that change and commit using `fixup` argument and specify the commit its intended to later fix.
```
git commit -a --fixup 0e217d2dd70
```

The commit history now looks like this. Note how it also has a text called 'fixup' that automatically gets added to it.
```
0e217d2dd70 APICallStatus > digitalCardEligibility
470cbf3517c APICallStatus > GetAuthorizationStatus
7fab88abf08 APICallStatus > CardHolders
0d0b3d1dbf6 fixup! APICallStatus > digitalCardEligibility
```

And now when an interactive rebase is done.
```
git rebase -i f31f60ff2a050dd48f1c385c2f660cf93b64535d --autosquash
```

the fixup commit automatically gets squashed onto the related commit.
```
pick 0e217d2dd70 APICallStatus > digitalCardEligibility
fixup 0d0b3d1dbf6 fixup! APICallStatus > digitalCardEligibility
pick 470cbf3517c APICallStatus > GetAuthorizationStatus
pick 7fab88abf08 APICallStatus > CardHolders
```

#### Cherry-picking

If you just want to bring in some selected commits from another branch into the current branch, a cherry-pick can be done.

Cherry-picking however does not bring in the exact commit ref but instead just brings in the changes and creates a new commit ref. So later if you actually merge that branch, all those commits are once again merged in just as it happens in a normal merge/rebase.

Hence, it is usually advised not to do cherry-picking. But instead just do a merge from a suitable branch.

```
git cherry-pick [commit hash1, commit hash 2]
```

#### Stashes

`git stash` - Creates a stash with the current changes <br>
`git stash push -m "Description"` - Creates a stash and assigns it the specified description <br>
`git stash list --date=local` - Gives a list of stashes <br>
`git stash drop stash@{8}` - Deletes the spcified stash <br>
`git stash show stash@{0}` - Shows the changes in the specified stash <br>
`git stash apply stash@{0}` - Applies the spcified stash <br>
`git stash push --keep-index` - Creates a stash without removing the changes from staging area <br>

#### Patches

Git patch allows to export individual commits into files that can then be applied to some other branch. And you could mail them to someone else as well so that they can also apply it to that destination branch and check it out.

`git format-patch master -o patches` - Creates separate patch (`.patch`) files for evert commit in the current branch which is not there in the compared branch, i.e. `master` in this case. The files are stored in the specified directory, `patches` in this case.

`git am <patch file path>` - Applies the specified patch file to the current branch

`git apply TestChanges.patch` - This too applies the patch.

`git stash show "stash@{0}" -p > TestChanges.patch` - Creates a patch file using the specified stash ID.

#### When merging a branch for an already existing PR on Github

> Be very careful while merging branches when you want to push the branch to an already existing PR after merging.<br><br> You need to make sure that you are doing a rebase, or else the commit delta in Github gets messed up.<br>If you are using Tower client, its better to directly pull the changes from the concerned remote branch (as then it also gives the option of doing a rebase), don't simply merge from another local branch (as it then does not give the option to rebase.)
