A shell program runs in interpretive mode, i.e. it is not compiled into a separate executable file as a C program is. Each statement in the program is loaded into the memory when it is to be executed, and consequently a shell program runs slower than that written in a high-level language.

Shell scripts are executed in a separate child process, which need not be the same type as the login shell.

There are a few differences in `bash` shell scripts compared to Bourne shell scripts. Mainly, `bash` evaluates `$0` differently and it also does not recognize escape sequences used by `echo` (like `\c` and `\n`) unless the `-e` option is used.

#### Shebang

Comments are given using `#`. However, in case of shebang (which is always the first line) it matters. The shebang line is the interpreter line, it always begins with `#!` and is followed by the pathname of the shell to be used for running the script.
```
#!/bin/sh
```
>  Clearly shebang matters. As giving a non-existing shell name in shebang causes the script to fail.

To run it first needs to be made executable (`chmod +x scriptName`), and then the entire path needs to be given as the script's path may not be in shell's `$PATH`.

When a script is running by explicitly using `sh` command, the shebang line gets ignored and instead the shell specified gets used.
```
sh scriptName
```

Shell scripts are executed by a child shell.

#### Making script interactive (`read`)

Values are read from the console using `read`.
```
echo "Enter a value"
read var1     # What user gets entered here gets assigned to var1
echo "User entered $var1"
```
Multiple values can be read together, the user would need to delimit them with space. Also, if user enters more values than `read` is accepting then all the extra ones get appended to the value of the last variable `read` reads.

`$REPLY` is the default built-in variable for `read`.
```
while isSomethingBeingReadByFind= read; do
    fileBeingScanned=$REPLY
    echo MARKDOWN\ FILE\ BEING\ SCANNED----\> \ $fileBeingScanned
done < <(find "$1" -name "*.md" -print)
```

#### Command line arguments

Arguments can also be passed during shell script invocation by delimiting them with space. They get stored in special variables, i.e. `$1`, `$2` and so on. `$*` stores all the command line arguments together, and `$#` has the count of no. of command line arguments passed.
```
Desktop (10:18 PM) $ /Users/sou543/Desktop/script.sh val1 val2
```
`$0` has the name of the command itself that was used to invoke the shell script.
```
Desktop (10:31 PM) $ bash /Users/sou543/Desktop/script.sh
$0 - /Users/sou543/Desktop/script.sh
```
If a command line argument has multiple words, then can be wrapped in `""` or the space can be preceded by `\` <br>
`$@` stores all the command line arguments in an array. <br>
`$?` gives the exit status of the last command.

#### `exit` and EXIT STATUS of commands

`exit` causes script to stop. `exit 0` indicates everything was fine, `exit 1` indicates something went unexpectedly wrong.

All commands return an exit status.

Keep in mind that each command/script has its own interpretation of what it treats as success (`exit 0`) and what it treats as failure (`exit 1` or something else).

Also, `exit` can terminate a script only if it runs in the same shell that's running the script. Hence (if at all), if a an `exit` is typically wrapped in a `{}` rather than `()`.

#### Conditionals

##### Logical operators `&&` and `||`

`&&` is the and operator, `||` is the OR operator. They both work well with the exit status of the command returned by either of their operands.
```
if grep "\(USA\|India\)" Sample.txt 2>dev>null && grep "Europe" Sample.txt 2>dev>null
```
Even this is possible. Here, the script stops (due to 'exit 2') if the first condition does not succeed.
```
if grep "\(USA\|India\)" Sample.txt 2>dev>null || exit 2
```

##### Comparison operators

`-eq` -  Equal to <br>
`-ne` -  Not equal to <br>
`-gt` -  Greater than <br>
`-ge` -  Greater than or equal to <br>
`-lt` -  Lesser than <br>
`-le` -  Lesser than or equal to <br>

Things like `-eq` can only be used for numbers. For comparing strings, plain `==` works.

```bash
if [ $EXTENSION == "md" ]; then 
   ...
fi
```

##### `if` condition

```
if grep "\(USA\|India\)" Sample.txt 2>dev>null
then
	echo "Pattern found"
else
	echo "Pattern not found"
fi
```
The condition placed next to `if` can actually be any executable program (probably as long as its in `SPATH`). However the value returned by such expression cannot actually be handled by `if`, and is instead handled by `test.` <br>

`elif` is also allowed, and should have its own `then`.

> Comparing strings in `if` can be done like this (the spacing around box brackets is important). <br> if [ "$2" = "str" ]


##### `test` condition

Here, 'x' and 'y' are checked for equality, and the exit status returned by `test` command for this check is printed. `test` is practically the 'if' command of Unix, as `test` can do equal and other comparisons. It returns a true or false exit status.

> `if` cannot be used here, probably because `if` works on exit status and not on 'true'/'false' values that get returned here (as there is no 'command').

```
test $x -eq $y; echo $?
```

There even exists a shorthand for `test`, that is `[]`. In fact `[[]]` too can be used, and it offers even more versatility in some way ([link](https://developer.ibm.com/tutorials/l-bash-test/)).
```
test $x -eq $y
[$x -eq $y]
```

It can even do string comparisons with `-eq` and `-ne` operators.
`-z` checks if the string is null.

```
if [-z "pname"] ; then
```

> Numeric comparisons work on integers only, and not on decimals. How to do decimal comparisons then?

The flags/operators such as `-z`, `-s`, etc. have specific meanings. Here are some of those.

`-s` - Not empty <br>`-z` - String length is zero <br>`-e` - Exists (also -a) <br>

These are all same things. What follows `&&` is an expression that runs if the preceding condition is true.

`````
$ test 3 -gt 4 && echo True || echo false    ------ false
$ [ "abc" != "def" ];echo $?   ------ 0
test -d "$HOME" ;echo $?  ------- 0
`````

##### `case` condition

The way it works is that the command listed in the entered choice gets executed.
```
case expression in
  pattern1) commands1 ;;
  pattern2) commands2 ;;
esac
```

`case` handles strings and numbers pretty well, but it does not handle relational(?) and file tests.

This runs `ps -f` if '2' is entered by the user.
```
echo "Enter your choice:"
read choice
case "$choice" in
	1) ls - ;;
	2) ps -f ;;
	3) date ;;
	*) echo "Invalid option"
esac
```

```
case `date  |  cut -d" " -fl` in    # 3 character day string
  Mon) ;;
  Tue) ;;
```

Patterns can be combined as well.
```
case "$answer" in
  y|Y) ;;
```

While matching strings it accepts wild-cards.
```
case ""$answer" in
  [yY][eE]*) ;;
```

##### `for` loop

```
for variable in list
do
  commands
done
```

```
for var in $PATH $HOME
do
	echo "Now"
	echo "$var"
done
```

If the list has wild-cards, the shell automatically interprets them as filenames.
```
for file in *.htm *.html; do
```

In case of `for`, `$@` is used to refer to the positional command line arguments.
```
Desktop (02:42 PM) $ /Users/sou543/Desktop/script.sh arg1 arg2
for pattern in "$@"
for pattern    # $@ is even implied by default
```

Both the loops support `break` and `continue` as well.

To iterate through all the files in a folder.

```bash
SCRIPT_DIR="$(pwd)"
for entry in "$SCRIPT_DIR"/* 
do
    ...
done
```



#### Working with variables

([SO link](https://stackoverflow.com/a/18136920))

To read a variable it must be prefixed with `$`.

`````bash
FILE_NAME=`basename "$entry"`  -- Here entry variable is read and used
`````

If there is a reason for ambiguity in variable name, then the variable name can be enclosed in `${}`.

```bash
var=foo
echo $varbar
# Prints nothing because there is no variable 'varbar'
echo ${var}bar
# Prints foobar
```



To run a command and get its output to a variable, the command needs to be enclosed as `$()` or enclosed in backticks.

`````
FILE_NAME=`basename "$varname"` -- Same as running 'basename $varname'
FILE_NAME=$(basename "$varname") -- Same as running 'basename $varname'
`````



If the variable name contains blank spaces, enclosing it in `"$VARNAME"` causes it to be treated as a single entity, which is especially useful when the variable has file paths.

```bash
WC_OUTPUT=$(wc -l "$FILE_NAME") -- This works even when FILE_NAME variable has blank space
```
